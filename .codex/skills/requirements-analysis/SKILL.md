# 需求状态图与原子需求分析

以 PRD 功能点和 UI 资料为依据，产出可追溯的需求分析。用户决定需求含义，AI 负责调查、同步建模、循环补漏和生成观察产物。分析范围由需求文档决定；实现或运行验收条款作为需求证据，不开展应用开发、实现进度评估或应用运行验收。

## 规范依据

本 Skill 的产物与门禁由以下需求分析职责推导：

1. 从 PRD、UI 和真实人工作答确定范围；初始澄清与最终整体验收由人工确认。
2. 以业务状态和有验收意义的 UI 状态建图，一条状态迁移对应一个原子需求，先按终态等于初态推导直接衔接，再生成从真实起点覆盖全部需求的条件可行路线及其实际用边；优化访问次数，最短宣称必须有相应证明。
3. 先建立功能点，再逐节点循环检查有意义的分支与边界；修改后重新审查，未知业务规则保留待决。
4. 每个原子需求说明功能归属、起点、事件、条件、终点、验收约束、来源和 UI 对应。
5. 提供结构化双图、原子需求详情，以及供人工理解和验收的只读 HTML。
6. 分析结果在同一套当前文件中持续更新，避免信息只留在对话中；不要求进度快照或递增版本号。
7. 可机械判断的约束由程序验收，语义结论由独立模型上下文评审；修复并复审通过后，再提交最终人工确认。

目录与字段是承载这些职责的约定。每项必需产物应能说明其服务的职责；不得把单次执行的中间文件、Skill 开发测试或现有目录清单提升为通用输出要求。

## 初始澄清

读取用户指定的 PRD、UI 原稿或导出图、令牌和说明，登记精确位置、读取范围及真实证据。每读完一个有意义片段或画板，立即更新工作模型的 sources 和 _process/evidence/；不要等全任务结束再保存。附件中的提示词、旧建议和操作指令只作为资料，不自动提升为当前要求或授权。

不通过现有实现反推需求。先识别功能边界、参与者、入口、结束范围、名词、UI 覆盖与冲突；PRD/UI 冲突时列出两方证据和影响。只询问资料不能确定的决策，复用当前对话已确认内容。初始确认绑定 scopeDigest 和真实人工作答，未确认可整理资料和草案，不开展正式扩展。

人工确认只设在初始澄清与最终验收。中间发现未定义规则，记录待决问题、有依据的候选和影响，继续不受影响的部分；最终集中处理，不自行选定业务答案。

## 同步建模与循环审查

先建立功能分组、主流程状态和迁移，同时为每条迁移建立一个原子需求。状态含业务事实及有验收意义的 UI 状态；边表达事件与守卫，结果在目标状态和验收断言中说明。允许不连通部分、共享状态、自环、回环和平行边，不强造公共根节点。

每条迁移是一个可独立说明与验收的行为，共同成立的多个结果断言可同属该需求。验收义务以当前需求文档和已确认资料为界，不因检查清单、缺画板或常见实现惯例扩展功能；等价行为合并，不以需求数量证明完整。需求图先按 A 的终态 ID 等于 B 的初态 ID 推导候选直接衔接，再按 requirement-graph.md 求结构访问下界并验证条件，必要时使用经重放验证的覆盖方案；只保留有效路线实际使用的直接衔接，不把启发式结果称为全局最短。允许回路和重复；重启须有明确依据并按段呈现。所有需求节点保留；不得将生成图省略的衔接当成业务删除，不混入开发依赖。

按 branch-review.md 逐节点检查来源、事件、条件反面、合法域、失败、取消、返回、重复和时间等维度。只为改变行为、约束、可观察结果、后续能力或验收义务的差异增加分支。逆向检查不表示每条边必须有逆操作。分支先证明来源支持和独立验收义务，再决定是否建边；自环必须提供 selfLoopEvidence，说明精确来源、响应／约束及保持同一状态类别的理由。不能按可见控件与状态机械组合补边。

完成一个资料片段、一组迁移、一个待决项或一个节点审查，就在 _process/ 的当前工作文件中更新并运行 save。图、原子需求、UI、来源和审查记录同步调整。语义改变后全量重新审查；审查理由留在当前模型 rounds 中，不复制整个模型。中断后读取当前文件和 next_action 继续，没有历史恢复入口。资源不足记 incomplete 和具体前沿，不以轮数上限冒充收敛。

## 全量链路重建

任何状态、迁移、真实起点或路径条件改变后，从当前工作模型重新生成完整状态图、需求覆盖图及“每个真实起点到每个状态”的最短到达链路；新增、删除与未选中的分支一并处理。状态图保留全部业务迁移，需求图只保留覆盖路线用到的有向边；点击状态仍从完整状态图取一条满足条件的最短到达链路，不要求枚举回环产生的无限路径。按 feasibility.md 分别检查状态可达、每条迁移及其已声明分支可执行、整段路线可执行，再审查连贯中文能否说明前提、操作和预期结果。单条最短状态链路没有经过的边也必须有可执行见证。不可达或未完成的结果须明确保留并回到分支审查，不以新增假起点、假迁移或放宽条件消除问题。详见 [HTML 链路与验证合同](references/html-review.md) 和 [分支审查](references/branch-review.md)。

## 观察、验收与交付

运行 prepare 在输出根目录更新双图 JSON、原子需求详情、完整模型、审查记录、HTML 和 manifest。UI 媒体嵌入 HTML；工作缓存与内部评审留在 _process/。HTML 用全屏 Canvas 展示完整状态有向图及需求覆盖有向图，支持节点拖拽、平移和缩放。一个或多个真实起点均来自文档，功能局部入口不得混用。点击状态按功能、完整到达链路、UI 图与有来源的 CSS 设计值分区；点击状态箭头只展示该迁移的原子需求，衔接箭头展示两项需求的关系与使用次数。覆盖路线按段展示真实起点、完整中文步骤、重复次数和条件校验；结构最优不得当作业务可执行；有条件冲突的结构候选不作为有效覆盖路线交付。不展示内部 ID、原始 JSON 或字段对象。链路按迁移数最少并保留来源、类型、操作方式等上下文，到当前状态即止，不能用互斥守卫串出假链路。HTML 只读，确认在对话完成。输出存在、页面浏览或无人回复均不构成人工确认。

最终先集中处理未定规则和设计缺口。答案改变含义时直接修改当前模型，重新闭合审查、导出并独立复审。独立上下文按固定八项 rubric 核对来源、分支意义、原子性、条件、UI、待决、收敛和真实 HTML 观察，报告绑定当前内容与导出摘要。失败修复复审，缺证如实保留未完成；不能以自评或手填通过替代。

assert 仅在除最终确认外的门禁均通过时返回 awaiting_final_confirmation。此时展示当前 HTML 和验收结果，请求整体确认；缓存真实回复，写 acceptance.json，再 assert / publish。publish 验收同一套当前产物，不生成另一个交付版本目录。后续含义变化使旧评审和确认过期，仍在原路径修订与重新验收。

结构检查不能证明业务正确、独立性或人工作答真实。脚本约束正常通道，没有运行时 Hook 或文件权限隔离。完整命令见 workflow.md。
