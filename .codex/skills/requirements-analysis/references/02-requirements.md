# 第二步：原子需求与需求图

## 验收目标

仅在第一步门禁通过后开始。每条已确认迁移对应一项原子需求，全部需求可从真实入口按条件可行的路线覆盖。需求图表达执行衔接，不表达开发依赖。

| 检查项 | 通过条件 | 验收方式 |
| --- | --- | --- |
| R-STRUCT | 满足需求 JSON 合同，绑定当前状态图，每项保留功能和视觉验收结构 | 程序 |
| R-MAPPING | 迁移与需求双向一一对应，引用、归属和断言来源有效 | 程序 |
| R-GRAPH | 所有节点保留；衔接、路线、计数与算法结果一致；无跳跃、无漏项、条件重放通过 | 程序 |
| R-ATOMIC | 一项表达一次迁移的独立行为，共同成立的断言未机械拆为需求；上层功能与持续静态约束未冒充节点 | 独立语义评审 |
| R-ACCEPTANCE | 功能／视觉验收适用性、前提、触发、结果及来源准确，遗漏与擅增均已排除 | 独立语义评审 |

只找到完整可行路线但未证明最优时，允许通过覆盖门禁，明确标为 `not_proven`。部分覆盖、条件未知或冲突不能通过。

## 初始化与每项需求的信息

从 [需求模板](../assets/requirements.template.json) 初始化；[需求 Schema](../assets/requirements.schema.json) 定义结构。

- 顶层 `stateDigest` 绑定当前完整状态 JSON；`requirements[]` 保存人工分析的需求；`requirementTraversal` 指定是否允许有据重启；`graph` 由算法生成。
- 每项含 `id`、`title`、`transitionId`、`featureIds[]`、`sourceIds[]`、`functionalAcceptance` 和 `visualAcceptance`。初态、事件、守卫和终态从迁移解析，不维护第二份真相。
- 两个验收结构均存在，均含 `applicability`、`reason`、`checks[]`，但不要求两者都适用。`applicable` 须有非空检查；`not_applicable` 须说明原因并保持检查为空；`unknown` 不能通过。
- 每条 check 含 `given`、`when`、`then[]`、`sourceIds[]`。视觉 check 另用 `uiRefs[]` 定位画板／区域或文字规范，可引用状态的视觉约束。功能与视觉检查均可同时适用。
- 行为有依据而验收内容未确定时回到澄清，不填“符合设计”“按各分支处理”等不可判定结果。禁止副作用属于功能义务时显式记录；共同成立的多个结果可以属于同项需求。
- 持续视觉规范留在状态。相关迁移的视觉验收可以引用它；无 UI 变化也可能需要验收已有呈现，具体以来源为准，不用中文前缀猜测视觉类型。

## 构建与求解

1. 逐迁移构建需求与适用的验收内容，核对双向覆盖。
2. 执行 `python SKILL_DIR/scripts/analyze.py requirements RUN --derive`：绑定状态摘要并生成 `graph`。它只生成派生图，不替用户填写需求含义。
3. 执行 `python SKILL_DIR/scripts/analyze.py requirements RUN`，完成机械检查；独立评审逐项核对需求原子性、功能／视觉适用性、断言与迁移／条件的一致性；报告覆盖全部需求并列出来源定位，绑定该步摘要后再重跑。

### 候选边与交付边

对任意需求 A、B，当且仅当 `to(A) == from(B)` 时生成候选有向边，记录共用状态。相同端点不意味着条件可同时成立。

最终保留全部原子需求节点，只绘制已验证覆盖路线中相邻需求实际使用的边，相同有向连接合并记录 `usageCount`。不跨重启分段连边；删除未用候选边不表示删除业务迁移。保留边集合不能任意拼接成新路线。

### 最少访问的既有算法

优化目标是覆盖全部需求的**总执行次数，含重复访问**；不是不同节点数、边数或需求数量。

1. 将每项需求视为对应状态边，访问下界为 1、每次成本为 1。
2. 在必需边按分量连通的结构模型上，用最小费用流补平衡，再用 Hierholzer 构建覆盖路线。默认不允许重启，枚举真实起点与终点求开放路线最优；使用残余网络与重新求解核对证书。
3. `restartPolicy=documented_entries` 仅在有来源或真实用户授权时可用，`authorization` 指向依据。重启成本为 0，分段从真实入口开始；不表示业务数据自动复位，不生成虚拟业务节点。
4. 对结构最优路线逐步重放条件。达到结构下界且重放通过，才可将这条条件可行路线称为已证明最短。
5. 若结构路线条件冲突，保留既有 `witness_cover` 启发式寻找可行覆盖。它不证明全局最短；失败也不能证明业务无解。记录 `not_proven`、结构下界和实际访问次数。

不把这套连通前提下的结构算法泛化为任意不连通必需边的精确算法。搜索未完成、无合法连续覆盖或需求未覆盖时保留失败／未完成，不能删节点、加假边或隐含允许重启。

## 产物与修改影响

`requirements.json` 内的 `graph` 含全部节点、路线实际用边、覆盖情况、分段路线、访问计数、条件检查与最优性说明。脚本重算验证，不能手填最优证书或单独修改图以绕过算法。

状态含义改变时先返回第一步；需求或验收改变时重新生成需求图并重查第二步。独立报告的输入摘要包含当前状态与当前需求，过期报告不能复用。
