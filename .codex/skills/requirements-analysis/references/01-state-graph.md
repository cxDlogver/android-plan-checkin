# 第一步：需求澄清与状态迁移图

## 验收目标

先明确范围与状态观察层级，再分析。完成的状态图须同时满足结构完整和语义完整：所有范围内来源义务有承载或有据处置；保留状态与迁移均合理；影响它们含义的疑问已经由资料或真实人工回答解决。只对当前明确范围作完整性结论。

| 检查项 | 通过条件 | 验收方式 |
| --- | --- | --- |
| S-STRUCT | JSON 满足合同，真实入口、状态、迁移非空；必要信息可判定 | 程序 |
| S-LINKS | ID 唯一，状态、功能、来源、覆盖记录引用有效；自环说明齐备 | 程序 |
| S-PATHS | 每个保留状态至少由一个真实入口可达；每条迁移及已声明条件分支均有可重放见证；逐入口最短到达链路已生成 | 程序 |
| S-CLARIFY | 无开放问题；已确认问题有答案、真实回答引用和可读取的澄清确认文档 | 程序核对记录，执行者核对回答真实性 |
| S-MEANING | 每个状态满足四项准入；每条迁移有独立义务，自环逐条成立；条件编码忠实于业务含义 | 独立语义评审 |
| S-COVERAGE | 双向来源覆盖与逐对象复核闭合，无未分析项；局部样例、参数、公共约束和澄清答案处置正确 | 独立语义评审 |

任一项失败则不能完成第一步。证据不足为 `pending`；不把未完成搜索当作不可达，也不把字段齐全当作需求清晰。

## 初始化与 JSON 合同

从 [状态模板](../assets/state.template.json) 初始化；[状态 Schema](../assets/state.schema.json) 定义结构。模板中的空集合和空文字只是草稿，不能通过完成门禁。

| 信息 | 必要语义 |
| --- | --- |
| `scope` | 目标、范围内／外事项、观察对象与层级、区分状态的验收维度和可变参数 |
| `sources[]` | 来源 ID、类型、位置、精确章节／画板区域、已读取内容摘要；可附版本或缓存 |
| `features[]` | 功能 ID、名称、来源；功能分组不等于状态或原子需求 |
| `entryStateIds[]` | 有资料支持的真实业务入口；在相应状态定义中说明入口前提，不按零入度猜测 |
| `states[]` | ID、名称、功能归属、可判定的当前定义、业务／UI 事实、视觉约束、来源 |
| `transitions[]` | ID、功能、初态、事件、守卫、终态、效果、来源；自环另有独立义务与同状态理由 |
| `coverage[]` | 每项来源义务、位置、映射状态／迁移，或范围外／不适用的依据；不以资料文件数量代替覆盖 |
| `clarifications[]` | 问题、影响对象、状态、解决答案、真实人工作答引用；有此类问题时用 `clarificationDocument` 指向确认文档 |
| `pathContext`（按需） | 将影响连续执行的业务条件投影为有限域，供路径与迁移重放；不执行任意中文守卫 |

状态视觉结构 `ui` 含 `applicability`、`refs[]`、`constraints[]` 和 `reason`。`applicable` 表示存在有依据的视觉义务；`not_applicable` 说明原因；`unknown` 表示尚不清楚，不能定稿。约束写明目标、预期与来源，可附有来源的 CSS；图片预览是可选数据，缺少截图不自动等于缺少需求。需要预览时，引用已有本地图片路径。

## 构建与澄清

1. 阅读 PRD、UI 和真实回答，登记精确依据；识别功能、入口、术语及冲突。资料缺失与建模没完成分别记录，只向用户询问无法自行查明的需求决定。
2. 先建立主流程，再逐状态核查事件、守卫补集与重叠、边界、失败及禁止副作用、取消／返回、重复／时间、角色权限／对象归属、UI、跨功能共享状态及结束边界。对适用项给出处理，对不适用项给出范围依据；这些维度只用于查漏，不产生新的需求。
3. 将需人工决定的问题写入澄清文档，说明依据、问题、候选及影响；收到回答后保存原意、回答位置和模型修改。文档可以持续维护，不要求每轮独立文件。不制造确认回复或以用户沉默代替确认。
4. 进行双向覆盖检查，合并等价状态，修正不合理迁移；语义改变后复核受影响部分，结束前对当前全部范围做一次完整复核。
5. 运行 `python SKILL_DIR/scripts/analyze.py state RUN`。输出包含确定性结果、条件见证、逐入口最短链路和语义评审所需摘要；独立评审报告补齐后重跑同一命令。

## 状态与迁移判定

- 状态表达“当前是什么”，事件表达“发生什么”。定义应有纳入条件与相邻状态的区分，不能只写“正常／异常／已操作”。
- 仅当差异改变行为资格、可观察结果、后续能力或独立验收义务时拆状态。仅名称、日期或样例数据不同则参数化；局部组件样例挂在所属状态，不机械组合成整页节点。
- 同一截图可以对应不同业务状态；一个画板也可以含多个局部视觉样例。持续颜色、字号和间距约束放在状态 `ui.constraints`，不制造“查看／展示”事件。
- 边必须有来源支持，明确初态、触发、条件和结果。目标状态及 `effects` 承载结果；不能因为两个状态存在就认定可以互相迁移。
- 允许平行边、回环和自环。自环只用于有独立可验收响应、且前后仍属同一参数化状态类别的行为，提供 `selfLoopEvidence`；不能隐藏弹窗、权限等实际状态变化。
- 缺失路径时回查入口、状态粒度、条件与资料，不补假入口或放宽守卫。多个真实入口可以覆盖不同分量，完成模型不要求强造公共根节点。

## 状态四项准入与迁移独立性

| 准入项 | 可复核的依据 |
| --- | --- |
| 精确来源 | 支持该状态的具体条款或画板区域；直接推导说明依据，不引入新业务选择。 |
| 当前边界 | 当前事实、纳入条件与相邻类别的区别，可据此判断一个实例是否属于本状态。 |
| 独立义务 | 相比最接近的同层级状态，缺少本状态会漏掉哪项已要求的验收；等价则合并，只换样例值则参数化。首个状态以来源义务建立基线。 |
| 验收目标 | 可检查的业务约束或 UI 区域、目标表现及判定，固定要求与可变参数分清。 |

用现有状态字段、coverage 定位和逐对象评审说明保存上述依据，不要求另建四份文档。拆分／合并理由说明比较对象和具体差异；不能只写“含义不同”。

新增迁移同时满足：有据触发或约束、区别于已有迁移的独立验收义务、初态—事件—守卫—效果—终态一致。控件可见或常见交互不能作为建边依据。守卫补集不自动等于成功路径，存在某操作也不自动推出逆操作。

共享状态合并前，核对对象范围、持久事实、来源、操作模式与后续能力；若合并会把不同入口的互斥条件拼成假路径，使用忠实的上下文或按有据差异拆分。不能清除条件来获得可达性。

## 复核闭合的最低证据

在当前内容最后一次变更之后，复核全部状态、迁移、来源义务和澄清影响。独立报告逐对象列出结论与来源定位，closure 记录剩余分析项及闭合理由；既有 coverage 承载来源义务，无需十维日志或多轮快照。

只有所有对象已审、范围内来源义务均有处置、无未分析前沿及未解决的需求问题时才闭合。资料不能读取或资源不足则保留具体缺口。每条自环须有单独结论，核对其独立响应／禁止副作用与保持同状态类别的理由，不能仅凭字段齐全通过。

## 条件重放合同

无附加条件的守卫使用文字 `true`。非平凡守卫需建立 `pathContext`，并由独立评审核对与原文一致；不能用空条件规则伪装已形式化。

- `domains`：变量的有限 `values`、中文 `labels`、`description`。
- `entryContexts`：每个真实入口的初始允许值；省略变量表示完整域，不表示任意重置业务数据。
- `transitionRules`：覆盖全部迁移，每项含 `reason`、`sourceRefs` 和析取的 `cases`。每个 case 可有 `requires`、`set`、`setFrom`、`forget`。
- `requires` 与当前域求交；空交集阻断。`set` 表达本事件有据的写入；`setFrom` 从效果执行前的变量复制同义枚举并保留相关性；`forget` 仅用于来源明确使旧绑定失效的事件。
- 可选 `stateConstraints` 含 `requires`、`reason`、`sourceRefs`，约束状态事实；不得以入口切换为由无据修改数据。

逐条核对中文 guard、状态 facts、effects／验收 then 与机器规则的一致性。进入空／非空结果的前提使用 requires；只有实际写入才能 set，失败、取消和读取不得无据改写持久事实。

逐状态链路在“状态＋条件上下文”上按迁移次数 BFS；逐边和逐 case 生成见证并正向重放。有限域以外的文字含义仍归语义评审，程序通过只证明该抽象内的结果。无法建立忠实抽象时保留未完成并继续澄清，不宣称一般业务条件已被证明。
