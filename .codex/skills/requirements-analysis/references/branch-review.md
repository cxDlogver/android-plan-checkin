# 逐节点分支审查与收敛

## 建模次序

先从来源识别功能能力、进入状态和主流程，建立初版状态与迁移，并同步建立原子需求。随后运行多轮逐节点审查，补充有意义的边界。审查是 AI 的内部工作，只有初始澄清和最终验收需人工作出确认。

每轮审查开始时记录 nodeIds，即当前全部状态 ID。逐节点、逐维度登记结论；本轮新增节点下一轮继续审查。修改状态事实或迁移守卫后，把该节点、关联迁移两端和受影响的共享节点纳入后续检查。为便于证明覆盖，闭合轮仍须全量复核，不只检查最近修改项。

## 每个节点的检查维度

每一维度都须有记录；不适用时说明本功能中的具体原因，不能用统一空话跳过。

| dimension | 检查内容 |
| --- | --- |
| sources | 已知 PRD 条款、UI 场景和人工作答是否覆盖；是否冲突或重复 |
| events | 此状态下用户／系统能触发的事件、无效事件、事件后可观察响应 |
| guard_complement | 现有守卫的补集在合法域内是否有定义；分支是否漏、重叠或冲突 |
| boundaries | 空／非空、零／正数、阈值内外、首次／末次等是否产生不同规则 |
| failure | 拒绝、失败、超时、部分成功是否适用且有依据；哪些副作用禁止发生 |
| cancel_return | 取消、返回、撤销、恢复是否有业务意义及来源；不可逆是否需明确 |
| repeat_time | 重复触发、重试、过期、时间变化、操作顺序是否改变允许行为或结果 |
| permissions | 角色、权限、资源归属等约束是否适用；单用户功能可以有依据地不适用 |
| ui | 可观察状态是否与画板、组件或视觉状态对应；缺稿是否明确标注 |
| cross_feature | 跨功能共享状态、汇合、回环、入口可达性与结束边界是否一致 |

检查反面不等于机械翻转。例如“有问题项则拦截”需要检查“无问题项”时是否仍因其他条件拦截；不能直接宣布无问题就一定提交成功。可暂停不必然意味着可恢复，可删除不必然意味着可撤销。

## 分支准入：先证明义务，再建边

逐节点检查是在已有需求范围内查缺，不是把每个控件与每个状态组合成迁移。新增迁移须同时满足：

1. 能定位到原文规定的触发、响应或约束；由已确认规则直接推出的必要情况须说明推导，且不引入新的业务选择。引用整份文档、控件可见或“常见交互”不构成支持。
2. 与已有迁移相比，至少有一项独立义务：允许操作、守卫约束、业务事实、可观察结果、禁止副作用或后续能力不同。只换词、换示例数量或重复列出共享规则不另建需求。
3. 起点、事件、条件、终点及验收断言一致，不因模型缺少合适状态而把真实变化画成自环。

新增时在 changes.meaning 说明差异与来源。资料不足以决定行为时，只登记问题和有依据的候选，不能补一个“正常应当如此”的正式分支；资料未提出的实现选择不自动转成必须人工决定的需求。

## 状态等价性与抽象粒度复核

在逐节点审查和最终闭合轮中，除了查缺边，还要核对可能被错误合并或无意义拆分的状态。重点比较共用 UI 的状态、来源于不同入口而汇合的状态，以及仅用“空、非空、成功、失败”等笼统名称描述的状态。逐对判断：

1. **是否同一业务事实**：核对对象范围、持久数据、选中对象、日期、权限和操作方式。页面外观相同不代表事实相同，例如“全局无计划”不等于“某天没有待办”。
2. **是否具有同一后续能力**：对比合法事件、守卫、可观察响应、禁止副作用和验收断言。只要有来源支持的行为差异，就不能仅因为界面相同而无条件合并。
3. **是否只是参数差异**：若无需改变事件集合及验收义务，优先在有来源的参数化状态或 pathContext 中表示；不因日期、数量、示例个数不同大量建状态。
4. **合并是否会制造假路径**：检查分别由不同入口到达同一状态后的上下文，下一步是否被错误地视为对所有入口均合法。若有限域无法忠实表达关联条件，应细分状态；不得靠遗忘上下文或放宽 guard 消除冲突。

结论在既有十维审查记录的 `cross_feature`、`guard_complement`、`sources` 中说明，并引用被比较的状态、迁移和具体来源；无需新增独立输出文件或机械门禁。发现不同状态实际上等价时合并并重建关联边；发现同一状态混入互斥业务事实时先复核来源再拆分。任一模型含义变化都必须触发全量复审，不用旧结论补写通过。

## 自环的附加准入

自环不是“点了但没有变化”的通用记录方式。只有原文规定了该触发下可独立核验的响应或约束，且同一抽象状态确实能表达前后事实时才保留。

每条自环在 transition.selfLoopEvidence 保存：

- sourceRefs[]：每项 sourceId 与 locator，定位支持这项义务的具体条款或画板区域；sourceId 必须同时出现在该迁移的 sourceIds 中。
- obligation：需要核验的具体响应或禁止副作用，不写“仍在本页”“按原规则处理”等空泛结论。
- stateReason：为什么前后仍属于同一状态类别。若数据参数变化，说明变化的参数和保持的控制状态；不能隐去新提示、弹窗、只读资格等有验收意义的变化。

程序检查这些字段和引用是否合法；独立语义评审逐条核对原文是否支持 obligation、是否重复、stateReason 是否成立。字段齐全与来源文件存在都不能替代此判断。缺少依据或独立义务的自环删除；需要新状态才能表达的，使用有资料依据的状态，不用自环遮盖。

例如，资料规定保存中防止重复提交，可以表达保持保存中且不产生第二次写入的约束。仅因“今日入口可再点击”而画“今日空态→自身”，没有新增义务，应排除。

选日、切月、编辑参数等可以在明确的参数化状态中表达；不穷举每个日期、数量或输入值。参数变化的结果仍须明确可核验。

持续视觉规范、统计公式和页面初入默认值属于状态约束或真实进入迁移的验收结果，不单独制造“查看规则”“展示大字号”或“初始化已进入页面”的自环。不要为凑边界清单新增无依据的失败、并发、权限或恢复能力。

## 入口、到达链路与跨功能检查

在 cross_feature 维度逐节点核对进入依据；在 guard_complement 维度及独立条件评审中核对沿途守卫，不能只看该节点是否有入边：

1. 为每个顶层真实起点定位来源规定的起始场景，例如“进入首页”；多个不连通流程可以各有起点，功能内部状态不能提升为起点。起点仍可能有返回它的边。
2. 对每个状态读取逐根到达结果。资料要求可进入的状态至少应能由一个真实起点在适用条件下到达；检查既有数据初入与操作后到达是否分别有来源，不能强迫用户重做历史操作才能进入既有状态。
3. 对无路径状态判断是漏迁移、起点证据缺失、状态抽象混淆、条件冲突，还是资料尚不能确定。只按来源修复；依赖业务选择的留待决，不为了连通而虚构“查看状态”等事件、放宽守卫或新设起点。
4. 对共享状态检查来源、对象类型、操作模式等条件在前后步骤是否保留。必要时细分状态或使用 model-contract.md 的有限域上下文；失败不能产生成功后的事实，导航不能无依据改变业务数据。
5. 更新后重新计算所有起点的链路，并把变化的节点、两端和共享上下文纳入复审。草案中的断链可以保留并明确未完成；已知应可达却无合法路径的问题未解决时，不能宣称完整或收敛。

每条迁移还须按 feasibility.md 提供从真实入口到执行该边的见证，并满足目标状态事实。整段覆盖路线须用累积上下文重放；各边分别有见证不能替代连续路线验证。错误的笛卡尔积组合按来源移除，合法缺口按来源补齐，不为连通而放宽条件。

可达性检查与分支审查互不替代：最短链路不一定经过每条边，故每条迁移仍须独立核对来源、条件和验收义务；也不因某条边未出现在最短链路中就删除它。

## 检查结论 disposition

- covered：已有状态／迁移／需求覆盖，relatedIds 指向对应实体。
- added：本轮新增了有意义实体；记录 differences、来源和 changes。
- pending_decision：资料不足，question 记录问题、候选及依赖；不把未知答案当事实继续推导。
- excluded_equivalent：与已有分支等价，说明为何验收义务相同并引用已有实体。
- not_applicable：说明本维度为何不适用于该节点。

reason 不得留空。evidenceIds 指向 sources；当确实只能由人决定时关联 question，并明确证据缺口。一个检查可以关联多条迁移；同一维度也可有多条检查记录。

## 每轮记录

rounds[] 每项包含：

```text
id, modelDigest, kind(build|audit), nodeIds[], checks[], changes[], openFrontier[]
```

build 记录初版主流程来源与结构变化。audit 为全量逐节点补漏；每个 nodeId 的十个 dimension 均有结论。changes 记录 add/update/remove 的实体、meaning 及 sourceIds。新增或修改后不得在同一轮直接宣称闭合，要在更新后的当前模型上再进行全量审查。

审查轮开始时记录当前 modelDigest；每完成一个节点就在 _process/ 工作模型的 rounds.checks 中更新并运行 workflow.py save，不等全部审完才补记录。节点审查不能同时改语义，先保存变更再以新摘要检查。闭合要求所有节点有该轮／该摘要的已保存审查。历史删除 ID 按 model-contract.md 的 retiredIds 和删除记录追溯，不忽略未知引用。

openFrontier 表示仍需继续分析的节点／实体；业务规则待决但已完成当前可分析工作的情况，可以移至 questions，不伪装成问题已解决。保持分析前沿与人工待决清单两者可区分。

## 进入最终审阅的条件

可以产出带待决项的 review_ready 草案。须说明：哪些分析已收敛，哪些分支仍因业务解释未定而是 candidate；不能将“可供人审阅”写成“需求已确认”。

review_ready 也必须有下面的闭合覆盖；pending_decision 可用于集中澄清，但 QUESTION-001 未通过不请求整体确认。空 rounds 或未完节点保留 analyzing/incomplete。

本轮无新增的闭合证据是：

1. 最后一次结构／含义变更之后，在当前内容摘要上完成一个全量 audit 轮；此前至少还有一个建模／审查轮。
2. 该轮覆盖当前全部状态及全部适用维度，不存在未审的新节点。
3. 该轮 changes 和 openFrontier 均为空；guard、边界及反向检查都有处置理由。
4. 未决业务语义和设计缺口完整列在 questions，未被隐含选定；UI、功能与原子需求的对应可追溯。

审查开始前运行以下命令，将当前摘要写入该轮 modelDigest；每完成一个节点保存其检查。全量复核结束后重新计算并核对摘要仍一致，再闭合该轮。禁止事后替换摘要把过期检查绑定到新内容；若含义已变化，须在同一模型中重新全量审查并更新导出。

```text
python <skill-dir>/scripts/model_tools.py digest <RUN>/_process/analysis-model.json
```

最终 confirmed 模型的闭合轮不应仍有 added 或 pending_decision 结论；曾经待决的项应根据人工作答更新为对应覆盖／排除结论。

最终确认之前，用户须处理影响当前正式模型的待决项：给出答案、选定候选或明确移出范围。任何导致模型含义改变的答案都触发重审和重新导出；最终确认须覆盖重审后的内容。

预算或时间不足、资料无法访问、抽象边界不清时，可以保留 incomplete 和精确前沿。不能设置“做满三轮就完整”或“连续两轮 AI 没想到就必然无遗漏”的结论。闭合只表示在已确认范围、来源、抽象粒度下完成了可复核审查。
