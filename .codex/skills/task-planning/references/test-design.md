# 测试与实现计划

1. 原子需求是逻辑测试项，多条断言不拆节点；不同数据/设备可有多个实例。起点、操作、目标与迁移一致。
2. 给出数据及合法来源。日期须有固定业务时区、相对今天的日期、原记录/规则/生命周期；异常说明注入与恢复。无夹具或控制方式标待准备，不能把中文守卫当作已准备数据。
3. 复用原断言，模糊处列缺口；“不写入”给出行数/内容/页面等证据。延期功能是范围约束，不造操作与测试节点。
4. 视觉引用画板区域、适用状态、令牌及文字。无画板不等于无行为需求；无规定的装饰不补。CSS 仅表达设计值，Native 的 dp/sp 映射须说明。共享视觉去重，不声称各状态都有独立画板。
5. 阅读修改点的调用方、数据依赖及已有测试，写清风险因果链。旧 PASS 不是本轮通过。稳定分页、缓存等独立保护义务有证据且主项未涵盖时才新增回归节点。
6. Plan 按可实现单元分解，共享先于页面，数据/查询先于消费者。列现状、差异、入口、应保持契约和完成条件；已有能力以核对/复用承接，不要求重写。
7. 开发仅必要 static/unit；SQLite 集成不能改名单测绕过约束。设备、功能、视觉、TalkBack、性能矩阵在所有开发完成后执行。
8. 需求覆盖率和实例通过率分别报告。图状态聚合所有必需实例/断言，重复访问不重复记逻辑覆盖，也不自动完成实测。

回归范围由当前人工作答确定；暂不考虑回归时只生成原子需求主项，既有代码调查保留供实现计划使用，不据此增加测试节点。
