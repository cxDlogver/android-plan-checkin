# Skill 编写与审查判据

本表用于创建或修改 Skill 时的**判断**，不是要求每个 Skill 新建同样的文件、状态或验收系统。

## 1. 触发与任务边界

- 能否用一段简短的描述说明 Skill 解决的特定问题和触发场景？
- 能否举出一个看似相近但不应触发的请求？
- 是否把某个领域内所有任务都错误地归入同一 Skill？
- 是否有不经授权新增工作、修改其他仓库或产生外部副作用的指令？

示例：
- 过宽：`在处理数据库、查询或模型时使用本 Skill。`
- 精确：`在新增或修改数据库迁移、审查迁移发布时使用本 Skill。`

## 2. 指令密度与信息组织

- 删除该段文字后，模型是否仍能安全、正确完成任务？如果能，优先删除。
- 是否重复通用概念，或者在主文件和参考文件重复同一规则？
- 详细分支是否只有实际命中时才读取？入口是否直接、准确？
- 是否误将一次性的操作记录、运行日志或冗余说明打包进 Skill？

## 3. 约束程度

- 需要判断和探索的工作是否被规定成唯一解法？
- 对容易出错且必须一致的操作，是否有复用现有固定工具的机会？
- 每条“必须”是否说明何时适用、为什么关键；是否有不必要的硬性前置动作？
- 是否把格式检查成功误写为业务正确或语义正确？

**判断方法**：高风险、高重复、可确定性验证的操作倾向低自由度；情境依赖大、合理方案多的任务倾向高自由度。允许在同一 Skill 中混合使用。

## 4. 可验证性与证据

- 对真正重要的要求，能否观察到预期结果及其证据？
- 文件存在、Schema 合法、测试退出码等客观结果是否可以程序检查？
- 语义质量是否有明确的输入依据、评估准则及不确定性处理？
- 有没有让 Agent 自行宣布“完成”，但没有观察真实产物的情况？

**门禁边界**：写在 Skill 里的校验要求是软约束；只有环境层固定触发并能阻断，才可宣称为不可跳过的门禁。不要将硬门禁当作所有 Skill 的创建要求。

## 5. 长任务与失败边界（按需）

以下仅适用于跨阶段、易中断、存在重要副作用的 Skill：

- 进度和关键决策是否及时写入可恢复的位置？
- 恢复时能否核对实际状态及输入/版本变化，而不是复述旧摘要？
- 工具失败、输入缺失、证据不足时，是否能够明确停止或降级？
- 对提交、删除、发送、部署等操作，是否避免无条件重复执行？

简单 Skill 不应因为本节额外创建状态机、日志体系、验收合同或重试框架。

## 6. 验证与迭代记录

静态检查与实际执行必须分开报告：

| 类别 | 可证明什么 | 不能证明什么 |
| --- | --- | --- |
| 静态检查 | 文件结构、命名、必填元数据、引用可访问 | 触发准确性、业务结果正确 |
| 场景验证 | 真实任务下的触发、执行行为和结果 | 对所有任务普遍可靠 |
| 失败场景 | 特定异常下的处理行为 | 其他未知异常都已覆盖 |

评审时给出 `PASS`、`NEEDS_CHANGES` 或 `NOT_TESTED`，附具体差异和所需修正。只将能够复现或有明确证据的问题写回长期规范；避免增加与问题无关的全局规则。
