# 实现与静态检查

## 1. 任务就绪

按 task-plan.dependsOn 建立实现依赖图。任务就绪以全部前置任务的实现与静态检查通过为依据，不读取 Test Case 的验收状态。计划中的动态测试命令不作为本阶段就绪条件。

任务 A、B 无依赖路径，文件读写集合及独占资源不冲突时可以并行。共有文件均为 read 时不形成写冲突；任一方修改同一文件时串行。构建缓存、格式化器、生成器等共享写入也需隔离。并行执行者分别保存输出，由一个汇总者更新实现记录。

先记录实现开始，再实现、核对 done 并记录完成时点，随后执行静态检查。失败后继续修改时更新实现完成时点并重跑受影响检查，保留先前失败输出。不要修改文件时间补造实施顺序。

## 2. 检查范围

| 检查 | 本阶段处理 |
| --- | --- |
| 类型检查、编译器只读语义检查 | 执行 |
| lint、格式只读校验、静态依赖或规则分析 | 使用项目已有配置执行 |
| 打包、安装、启动宿主 | 实现本身需要时进行，不能据此认定 Test Case 通过 |
| 单元、集成、设备或浏览器行为验证 | 留给验收阶段 |
| 截图、DOM、原生节点树、业务结果比对 | 留给验收阶段 |

命令名称不能单独证明其为静态检查。读取 package scripts、构建脚本等实际配置，确认没有隐含测试或交互验收。自动修复属于代码修改，修改后再执行只读检查。

只检查已配置且适用于改动的静态规则，不为检查数量额外引入工具。记录不适用项及原因。原有静态问题影响判断时保留具体诊断和范围，不把失败改成通过。

## 3. 中断与修复

恢复时读取实现记录、源码差异与检查输出，核对摘要。源码、命令配置或相关依赖变化后，旧检查不能继续证明当前实现通过。

验收发现实现缺陷时，返回本 Skill 修复对应任务并完成静态检查，再交回验收。修复过程不修改用例状态或历史验收证据；验收阶段识别失效项并安排必要重验路径。
