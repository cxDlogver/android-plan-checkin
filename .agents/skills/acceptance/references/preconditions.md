# 前置条件与产物隔离

## 1. 进入验收准备

从当前任务规划原件开始，执行只读入口：

~~~text
python -B <skill-dir>/scripts/route.py preflight --workspace <root> --cases <规划test-cases.json> --plan <规划task-plan.json> --implementation <implementation.json>
~~~

`status=ready` 只表示允许进入验收准备：需求与来源、用例和路线校验有效，且当前版实现及适用静态检查全部为 implemented。输入缺失、摘要变化、静态检查失败或失效时，报告具体文件与原因，先回来源阶段补足；不能删去检查获得放行。

不要把“尚无验收索引/合同/会话计划”“宿主尚未启动”当作不能进入验收阶段的理由。这些是验收应完成的准备工作。规划中的 missing 是当时基线，不是永久阻断；是否满足，须由本次实际准备和观察证明，不能只手改 ready 标签。

## 2. 准备与正式执行门禁

| 准备动作 | 可观察的完成依据 | 未完成时处理 |
| --- | --- | --- |
| 审查驱动与断言入口 | 命令、cwd、入口文件及所需依赖可定位；覆盖目标环境、真实操作和规定证据 | 补齐或修复正式脚本；不因计划中列有命令就声称可执行 |
| 审查候选准备方案并运行 plan | 会话区间完整覆盖既定 coverage.sequence，必要重复、输入和 Mock 生命周期保留 | 修正候选能力或准备方案，不改需求路线缩小范围 |
| 运行 init 建立隔离副本 | 四份原件来源与 SHA-256 已保存；副本路径、引用、每例合同及视图一致 | 拒绝覆盖原件或已有副本；已有本轮记录按恢复流程处理 |
| 生成并核对执行清单 | init 后从正式索引生成 execution-plan.json/md/html；轮界、完整顺序、实时 next 和来源一致 | 补齐清单并运行 sync/check；规则见[验收执行计划](execution-plan.md)，不提前作为进入准备阶段的条件 |
| 启动/连接所需宿主并准备数据 | 实际宿主身份、构建、逻辑窗口、输入、Mock 边界、取证能力与合法初态可观察 | 只阻塞依赖该前提的访问；不得伪造操作或实际结果 |
| 按 next/begin/submit 执行 | 前项关闭并同步，本项所需前提有实际依据；每次 submit 等待 canAdvance | 当前失败/缺证据/不同步立即停止，登记后修复 |

运行 `begin` 只授权记录当前访问，不证明宿主与数据已就绪。驱动须在产品动作前观察实际 given；缺前提时按 blocked 提交实际阻碍，不能填造 operation/target。索引、合同和环境准备不算产品用例通过。

## 3. 复制范围与写入边界

默认复制到 `<workspace>/plan/acceptance/`；显式记录路径使用其父目录。必须先复制任务规划的 `test-cases.json`、`test-cases.html`、`task-plan.json`、`task-plan.md`，再修改副本。状态图、原子需求图、原 PRD/UI 和 implementation.json 保持只读引用，不复制一套需求事实。

`planningSource` 保存四份原件的路径和原始字节摘要及验收根目录；`testCasesPath`、`taskPlanPath` 指向验收副本。副本重定位相对 path 和 impact.changedFiles，保持实际引用目标；命令仍以声明 cwd 解析。副本 task-plan 只同步用例摘要与展示，不据验收结果改写实现完成结论。

init 为新验收记录建立独立结果；原件已有历史结果保留在来源中，不继承为本轮通过。已有本轮记录及失败不能重置或覆盖。每次写入前检查目标只在验收根目录内，并核对四份原件摘要；原件基线发生变化时先审查新版本，不静默重新绑定旧结果。

未隔离的旧索引不允许 submit/sync 写回规划目录。先保留其历史并审查迁移，再在副本上恢复；不通过删除索引、锁或失败材料绕过隔离检查。旧批次核对不授予新路线的推进权限。
