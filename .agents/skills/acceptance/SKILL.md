# 验收

## 1. 输入与完成单位

读取任务规划原件 test-cases.json、task-plan.json、状态图、原子需求图、引用的原始资料和 implementation.json，核对范围、直接来源与当前版本。先运行 `route.py preflight`；输入校验与实现交接门禁通过，即可进入验收准备。驱动补齐、宿主启动、会话规划和合同生成属于本阶段准备工作，不要求它们在进入本阶段前已经完成。可执行步骤与分层放行条件见[前置条件与产物隔离](references/preconditions.md)。静态检查不替代行为或视觉验收。

初始化时先将任务规划的 test-cases.json/html、task-plan.json/md 复制到验收根目录，记录原件路径和摘要，重定位副本的相对引用。之后只修改验收副本、合同和验收记录，禁止写回任何任务规划原件。原件已有失败历史保留；新轮结果不从旧记录推定，已有验收记录按原轮恢复。

Test Case 是验收定义；coverage.sequence 中一次出现是一次路径访问，以 visitIndex 区分重复。一次访问的全部适用检查通过、合同和证据已登记、JSON/HTML 已同步核对，才允许进入下一项。用例最终 passed 还要求其全部必要访问完成。

## 2. 按路径规划集中验收

保留原路径的顺序和必要重复节点，先核对哪些连续用例能够共享驱动、环境准备和数据上下文。声明候选准备方案的能力、必要资源、可执行访问范围及上下文隔离要求，再用 [schedule.py](scripts/schedule.py)规划分组。

在已审查候选方案与既定路径内，依次最小化：额外进入或重放节点数、环境准备单元次数、执行会话数。共享环境不得改变对象、数据或 Mock 的生命周期。分组只改变脚本边界，不跳过节点或改变需求路径；算法和字段见[路径与执行规划](references/route.md)。

init 后、首项执行前，必须生成并核对 execution-plan.json/md/html，列出每轮边界与划分依据、逐项初态/操作/预期/检查/后继及实时 next。R01、R02 是连续逻辑轮次，不等于进程会话；分组、成本边界与固定执行循环见[验收执行计划](references/execution-plan.md)。只给原则或轮次编号不算计划完成。

一个脚本可以覆盖多个用例，复用一次启动和就绪等待。每次访问仍须暂停并提交；同次访问的多环境检查在当前提交点汇合，不先按环境各扫完整条路线。全局约束、适配矩阵和直接影响回归按既定序列执行。

按已授权范围选择 script 或完整验收。仅脚本范围保留 browser 待验收；浏览器是后继前提的唯一证明方式时停止，不借范围选择跳过。

## 3. 为每个 Test Case 建立 JSON 合同

正式执行用例前，从验收副本生成 contracts/<caseId>.json，每个用例一份，覆盖它的全部必要访问。合同保存来源与定义摘要、初态、操作、预期事实、验收规则、数据与 Mock、逐次实际结果、预期与实际比对、证据和当前状态，见[用例合同](references/case-contract.md)及 [Schema](assets/test-case-contract.schema.json)。

未执行项保留空实际结果。动态预期按规则和当前输入独立解析，在动作前确定；不将设计稿样例固定为测试数据，不从被测输出反推预期。合同定义从正式 Test Case 生成，不通过手改合同获得通过。

在实现交接后编写或补齐断言，可复用已有驱动、启动器和正式脚本，不要求一用例一脚本。只执行用例规定的检查，不扩张大量额外测试。视觉和功能事实分别按所需类型、环境与证据验收。

固定输入使用规定值，动态对象、日期、版本及前序数据沿真实上下文解析。只 Mock 声明的外部依赖，记录命中、参数、次数与恢复；不 Mock 被测动作、目标画面或判定。原生截图、节点树及布局必须来自实际宿主；运行器只证明它可观察的结果；浏览器 DOM 与截图归为 browser。设计图作为预期图展示，不登记为实际证据。

## 4. 执行、同步与推进门禁

1. 从 execution_plan.py next 实时读取当前工作，与 route.py next 核对下标；门禁允许后 begin，并同步核对执行清单，观察真实初态与数据。
2. 执行操作并观察终态，逐项保存独立预期、实际结果、判定及必要证据。
3. 调用 submit，将当前访问写入验收索引、对应 JSON 合同和验收副本 test-cases.json，由同一数据源更新副本 HTML，并同步验收副本 task-plan 的引用摘要及 Markdown。
4. 只有当前访问 passed，且 recorded、synced、checked、canAdvance 均为 true，再通过 execution_plan.py sync/check 并重新查询 next，才继续。失败或阻塞也立即同步，不能等整批结束后再更新状态。

修复、会话收尾或恢复提交后也重建执行清单。中断时按活动访问和已登记结果恢复，保留仍有效的已通过项；上下文丢失只重放经核对的必要进入前缀。失败、缺检查、缺证据或同步中断时停止；未执行后项不预填通过。提交已经登记但投影中断时恢复同一提交，不重复产品操作来补登记。重复用例尚有后续访问时汇总可以为 partial；当前访问已通过并同步后可以按路径继续，整例不能提前标为 passed。

使用 [route.py](scripts/route.py)及 [acceptance.schema.json](assets/acceptance.schema.json)维护计划、合同、活动访问和结果。驱动必须实际等待推进门禁；工具不能阻止绕开入口直接操作应用，不能把规范文字当成已部署的运行时阻断。命令和状态见[证据与状态](references/evidence-and-status.md)。

## 5. 未通过时进入修复，再继续验收

保存失败现场并暂停路径，定位预期、实现、脚本、数据、Mock 或环境中的原因。通过 repair-open 登记原因、实际依据与影响范围；未完成修复流程时不得重新 begin 或跳到后项。

代码缺陷回[代码执行](../code-execution/SKILL.md)修复并完成静态检查；Test Case 预期不符合正式规范时，依据[任务规划中的用例规范](../task-planning/references/test-cases.md)仅修正验收副本，并以原 PRD、UI 或授权规范审查新预期；需要改变任务规划基线时返回该阶段另行处理，验收不得直接改原件。不得依据实际输出降低标准，也不得修改需求事实来让失败通过。

修复脚本、数据、Mock 或环境时，修复对应边界及恢复行为，保留原失败。通过 repair-close 核对修复证据与当前交接，再从最早受影响访问的合法初态重新验收。修复完成只解除暂停，不将 Test Case 改为 passed；必须实际重验并同步后继续。分类、预期修订和恢复规则见[失败与修复](references/repair.md)。

## 6. 审查、最终门禁与产物

核对真实路径、每份合同的定义与比对、全部必要证据、动态数据与 Mock 边界，以及当前源码和脚本版本。check 只表示记录、合同与视图一致；结构检查不能代替需求和证据语义审查。

finish 通过必须同时满足：全部必要访问及适用检查通过；无未关闭访问或提交；无未完成修复；所有执行会话真实成功收尾；合同、JSON、HTML 与相关视图一致。仅脚本范围通过时明确 browserPending，不能宣称完整验收通过。

默认验收根目录为 <项目根目录>/plan/acceptance/；未指定记录路径时，工具使用该目录的 acceptance.json。显式指定其他记录路径时，以该文件的父目录作为验收根目录。脚本、证据和临时输入的目录约定见[默认产物目录](references/evidence-and-status.md#11-默认产物目录)。

最终保留 acceptance.json、execution-plan.json/md/html、原件来源与摘要、每例一份的 contracts/*.json、正式验收脚本、必要成功/失败/修复证据，以及验收目录内同步的 test-cases.json/html、task-plan.json/md 副本。既有批次记录可用 execution.py核对证据，但不提供逐项推进授权，也不能转换为虚构的新访问。

任务完成后删除本任务创建的候选准备方案输入、计划草稿、探索脚本、临时截图和中间报告；必要失败证据、合同定义及实际结果历史继续保留。已有记录恢复使用，不初始化覆盖或删除失败来获得通过。
