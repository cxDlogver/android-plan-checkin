# 状态迁移与原子需求分析

先读[状态图数据契约](references/contract.md)，使用[状态图Schema](assets/state-transitions.schema.json)；派生原子图时读取[原子需求图规范](references/atomic-requirements.md)，使用[原子图Schema](assets/atomic-requirements.schema.json)。

本Skill定义通用的需求状态建模方法。业务实体、页面结构、文案、端型、断点、尺寸和资源取值均以输入的PRD及授权UI资料为准。下文示例仅说明判定方法，实际纳入内容由正式需求来源确定。

## 完成条件

- 状态由范围内可观察、可验收的事实构成；视觉事实与功能事实均可独立成态。
- 状态source直接定位原需求文档或UI；视觉状态关联结构节点和原截图。
- 每条迁移内嵌自己的operation。动作属于明示要求或到达目标事实的必要步骤。
- condition仅用于动作后存在不同结果的真实分支。同组分支互斥，初态—动作—条件确定唯一结果。
- 已确定的前提和全局规则持续适用，只登记新增或发生变化的事实。
- 最终状态图只包含states、transitions、constraints三类内容及必要文件元数据。
- 每条迁移恰对应一个原子需求；普通进入须前项终态等于后项初态，起始需求可随时重入。精确求得覆盖全部需求且总访问次数最少的序列，仅保留该序列使用的边。
- 两张图各自的JSON和HTML同步，原子图绑定同版状态图；分析、澄清与校验过程资料在完成后清理。

## 1. 确定需求与澄清

本节的独立工作记录由[analysis-work.schema.json](assets/analysis-work.schema.json)约束，覆盖资料登记、范围分类、澄清和定稿审查。[state-transitions.schema.json](assets/state-transitions.schema.json)只约束最终图。字段说明见[独立工作记录约束](references/contract.md#独立工作记录约束)。

开始任务时运行以下命令，在最终图目录创建.work/analysis-work.json：

~~~text
python <skill-dir>/scripts/work.py init <output-dir>/state-transitions.json --workspace <project-root>
~~~

初始化程序依据analysis-work.schema.json的const、default和字段类型建立工作记录，不读取独立template文件。.work中的记录在任务完成后删除；analysis-work.schema.json作为规范保留。最终状态JSON及HTML只包含状态、迁移和全局约束及文件元数据；原子图引用该正式状态图，不增加过程字段。

| 执行步骤 | 工作记录字段 | 与最终图的联系 |
| --- | --- | --- |
| 1.1 资料登记 | documents | 最终source直接指向其中核对过的正式文档或UI |
| 1.2 范围分类 | requirements及纳入项的actionAnalysis | 先识别事实与必要动作，再映射到最终states、transitions或constraints |
| 1.3 澄清触发 | clarifications，status=open | 对应未确定内容暂不定稿 |
| 1.4 澄清处理 | answer、resolution及必要的resolutionSource | 用实际回答更新事实和动作；需求改变时定位已更新的正式来源 |
| 2.5 确定起点 | entries | 逐个核对起点的进入或准备依据，无边状态说明独立验收依据 |
| 7.1 语义审查 | reviews、graphSha256 | 结合逐项依据核对本版图的范围、覆盖和判断 |
| 第8节收尾 | 完成双图校验后删除工作副本 | 最终交付状态图与原子图各自的JSON和HTML |

### 1.1 资料登记

分析依据包括当前PRD及用户指定的补充资料。每份资料填写documents中的一项，记录source、资料角色role、使用依据authorization和资料版本version；未标版本时version=null。按下表核对资料，正式文件的位置与哈希用于建立最终直接source。

| 登记项 | 记录要求 |
| --- | --- |
| 文件路径 | 记录实际读取的位置；最终引用使用相对分析JSON的路径 |
| 使用依据 | 明确资料由PRD引用，或由用户指定，以及它用于确定什么要求 |
| 文件版本 | 使用资料标注的版本；工作记录中可注明未标版本，最终source不虚构版本号 |
| 文件哈希 | 按实际文件内容计算SHA-256，用于检查引用是否失效 |
| 条款原文 | 摘录支持事实、动作或规则的原文，保留原意 |
| 条款位置 | 使用行号、真实章节或JSON Pointer定位 |

PRD确定验收目标和范围；授权UI资料具体化可见内容、结构及样式要求。实现代码、界面示例文字和历史资料按其授权用途使用。

### 1.2 范围分类

逐条核对本轮验收责任，在requirements中记录直接source、分类classification、理由reason及图内目标targets，区分以下三类：

| 分类 | 判定标准 | 分析用途 |
| --- | --- | --- |
| 纳入 | 本轮需要实现或验收的要求 | 建立状态、迁移或全局约束 |
| 排除 | PRD或用户明确指定为本轮范围外的要求 | 确定范围边界 |
| 上下文 | 背景、术语或已有产物现状 | 解释纳入要求的含义 |

对纳入要求分别识别视觉事实和功能事实。视觉事实描述可观察的界面表现；功能事实描述数据、规则或操作结果，两类事实均可独立构成状态。正式图中的每项内容都应在纳入范围内有直接依据。

每项纳入要求的targets至少定位一个最终状态、迁移或全局约束；每个最终实体至少由一项纳入要求覆盖。排除和上下文的targets为[]。这份映射只保存在工作记录，最终实体的source直接引用原文档或UI。

从原文和授权UI识别需要验收的事实，以及到达或改变事实所需的动作，再回填targets。每项纳入要求填写actionAnalysis，逐条说明候选动作、预期结果及处理结论；可以从初态和目标事实确定的必要步骤按第3.1节登记。没有动作时，写明核对范围及判断依据。动作识别覆盖本项要求的全部内容，不能仅由现有图中的实体反推。

### 1.3 澄清触发条件

出现以下任一情况时，向用户澄清：

- 需求存在多种解释，且不同解释会得到不同的事实、动作、终态或验收结论。
- 动作的执行者、作用对象、输入或结果缺少必要信息，导致迁移无法确定。
- 资料之间存在影响验收的冲突，且没有约定优先级。
- 无法给出事实的观察方法或明确的通过条件。

### 1.4 澄清处理

每个待决问题填写clarifications中的一项，记录question、impact，必要时填写proposal。待用户回答时status=open，answer和resolution为null。

收到实际回答后，在answer中记录text和conversationRef，在resolution中记录处理结论，将status改为resolved，再更新相关事实和动作。建议、预选项或用户未回复均不作为确认。

已确定部分可以继续分析；影响当前模型的问题得到回答后，相关部分才可定稿。用户回答改变正式需求时，将确认内容落实到原文档或正式补充需求中，在resolutionSource中记录该正式位置，供最终source直接引用。

本节的资料、分类和澄清统一保存在工作副本中，用于持续分析及断点续做。open问题、未完成审查或失效引用由工作校验报告提示；处理完成后按第8节删除副本，保留正式需求与最终图。

## 2. 建立状态

### 2.1 将要求写成可判定事实

每项事实回答三个问题：观察哪个对象、观察它的什么属性或内容、期望得到什么值。事实可写成“对象.属性 = 期望值”。

| 要求表达 | 可登记的事实 | 观察方式 |
| --- | --- | --- |
| 详情区域处于展开状态 | 详情区域可见=true | 查看该区域及其内容 |
| 已选中“选项B” | 选择控件的选中值=选项B | 查看选中标记及对应内容 |
| 数据已提交 | 目标数据的提交状态=已提交 | 使用需求已明确的查询或其他观察渠道 |
| 页面显示操作完成提示 | 提示区域可见=true，提示内容=操作完成 | 查看提示区域及文字 |

每项事实都需满足以下要求：

1. **有依据**：本轮需求要求验收该事实；source可直接定位支持它的文档或UI。
2. **能观察**：写出观察方法和位置，使验收者能够检查当前事实是否成立。
3. **能判定**：写出期望值、有限取值或所引用的UI标准，使检查有明确的通过或不通过结果。

“正常”“页面完成”“处理成功”等表述应先具体到以上三个问题。读取“操作完成”提示只能确认提示的视觉事实；实际功能是否完成，按需求要求的功能观察渠道分别确认。

视觉事实写入visualFacts，功能事实写入functionalFacts。没有对应事实时保留[]；至少一个数组非空。

### 2.2 将同时成立的事实组合为一个状态

一个状态只组合当前场景中能够同时成立、并且用于识别或验收该场景的事实。页面和组件清单用于定位来源，是否独立成态按事实差异和第2.3节判断。

- “主体区域可见”和“详情区域展开”可以同时成立，属于同一个状态。
- “详情区域展开”和“详情区域收起”互斥，分别属于不同状态。
- 不同页面、不同弹层表现或不同结果，先按需求列出事实，再按2.3判断是否分别建态。
- 加载中若有需求要求验收的遮罩、进度或禁用表现，可建立对应视觉状态；仅描述内部函数执行、请求处理中而没有需验收事实的阶段，不建立状态。

状态的事实是本轮验收需要检查的内容。对象未变化的其他属性、此前已成立的前提和全局规则按2.4沿用。

### 2.3 判断新建、复用还是不建状态

比较候选场景与已有状态，按下表处理：

| 比较结果 | 处理方式 | 例子 |
| --- | --- | --- |
| 需验收的可见内容、选中值或结构不同 | 分别建立状态 | 区域收起／展开；切换选项后显示不同字段组 |
| 需求要求区分的功能结果不同 | 分别建立状态 | 数据未提交／已提交；提交失败后输入保留 |
| 表现相同，但已有前提会改变可执行动作或后续结果 | 分别建立状态，并在各自初态写明该前提 | 同样显示详情页，但一组允许编辑，另一组只有查看权限 |
| 事实标准相同，后续动作及结果也相同 | 复用已有状态 | 从两个入口进入相同详情，且相关前提一致 |
| 仅样例参数不同，需求的事实标准和迁移规则相同 | 使用动作输入或验收数据，复用状态 | 输入名称甲／乙，均满足相同字段规则 |
| 仅为验证已有全局规则而改变窗口、字号等输入 | 在该规则或其引用矩阵中验收，不增加状态或自环 | 同一UI按既定规则检查宽度W1和W2 |

判断的对象是需求要求区分的事实，而非任意数据变化。若甲、乙对应不同校验结果或不同视觉验收标准，则按发生差异的行处理。

合并状态前须同时确认：验收标准相同、后续可执行动作相同、动作在相同输入下的结果规则相同。差异无法从来源判定且影响结果时，按第1节澄清。

### 2.4 处理已知前提与路径汇合

先确定事实所属对象及其生效范围，再判断是否沿用：

| 情况 | 处理方式 |
| --- | --- |
| 同一对象的事实已经成立，当前动作未改变它，也未发生使其失效的事件 | 继续沿用，在后续步骤中不重复登记 |
| 动作改变了事实取值、切换了对象，或原事实已经失效 | 按动作后的事实确定终态 |
| 多条路径汇合，后续动作需要的前提在每条路径上均相同 | 可以汇入同一状态 |
| 多条路径汇合，相关前提不同且影响后续动作或结果 | 保留为不同状态，分别说明前提 |
| 某条路径的必要前提未知 | 澄清或补足来源，暂不将其视为已成立 |

例如：先确定“目标对象允许编辑”，随后展开该对象的详情区域；若中间没有权限变化，继续沿用编辑权限，无需再次建立相同约束。若另一路径进入的对象只有查看权限，且后续可执行动作不同，则两条路径应保持为不同状态。

全局约束对全图统一适用。特定对象的权限、当前选择等局部事实保留在对应路径的初态，不提升为全局约束，也不改写成动作后的分支条件。

### 2.5 填写状态字段与确定起点

| 字段 | 填写要求 |
| --- | --- |
| id | 图内唯一且稳定的状态身份；修改措辞时沿用原id |
| title | 简短指出当前场景，例如“详情区域已展开” |
| statement | 将本状态需同时成立的事实写成可读陈述 |
| isInitial | 能作为本分析范围的直接入口或通过已明确的验收准备进入时为true |
| source | 直接定位原文档或UI；不得引用分析摘录、问题或审查记录的ID |
| functionalFacts | 本状态需要验收的功能事实，没有时为[] |
| visualFacts | 本状态需要验收的视觉事实，没有时为[] |

每项事实包含statement、assertion和observation：statement说明事实，assertion记录判断对象与期望，observation记录怎么观察及在哪里观察。字段格式见[状态契约](references/contract.md#状态)。

视觉状态的source包含结构JSON、节点和原截图。matches-ui断言引用该结构，具体布局和样式按其适用规则解析；原截图用于展示来源。

起点可以有多个，分别对应需求允许直接进入或准备的场景。isInitial标记全图的分析入口；from是某一条迁移的初态，任意状态都可能作为from，两者含义不同。起点标记表示本次分析从哪里开始，不指定产品默认启动页。非起点状态必须有范围内动作可达；到达步骤不清楚时，核对来源或澄清，不用起点标记掩盖缺失步骤。

每个起点在工作记录entries中登记stateId、入口类型、直接来源及实际进入或准备方法。来源定位支持该入口或独立准备方式的原文，并保留在状态source中；UI外观和页面覆盖清单分别支持视觉事实与覆盖范围，入口依据另行核对。没有入边也没有出边的状态，在isolationReason中说明其独立验收依据及范围内没有前驱、后继动作的原因。来源不能确定入口或状态间关系时，按第1节澄清。字段见[起点依据](references/contract.md#起点依据)。

### 2.6 完成状态检查

逐个状态核对：

- 可以指出其直接来源，并逐项说明事实的对象、期望与观察位置。
- 状态内事实能够同时成立；至少有一项视觉或功能事实。
- 与其他状态的差异符合2.3，等价场景已复用。
- 沿用的前提符合2.4，影响后续结果的差异已经表达。
- 全局规则和未变化的前提只在原有位置维护。
- 每个起点有对应entries及实际进入或准备依据；无边状态有独立验收说明，非起点有到达路径。
- 对照纳入要求核对到达和改变这些事实的动作，相关候选动作均有处理结论。

## 3. 建立迁移

每条迁移记录from、to、operation和直接source。operation包含动作名称、执行者及实际需要的input，直接内嵌于迁移，不设置动作ID或独立动作表。

### 3.1 动作依据

动作可包括界面呈现、选择、输入、滚动、环境设置及需求内功能操作。按以下标准判断动作依据：

| 动作依据 | 成立条件 | 审查要求 |
| --- | --- | --- |
| 明示要求 | 正式需求直接说明该动作 | 核对执行者、作用对象、输入及结果 |
| 必要步骤 | 初态和目标事实已确定，能够据此确定使两者发生迁移的动作 | 说明动作改变什么、如何到达终态，确认效果属于本轮范围 |

动作的执行者与场景应明确。验收场景中呈现指定样例、设置环境的动作按该场景表达；产品中的交互路径需要对应的产品需求依据。每条边表达一个可独立验收的动作，实现过程无需逐步骤进入图。

候选动作保存在所属纳入要求的actionAnalysis中。已建迁移记录其初态、内嵌operation、预期结果和迁移引用；范围外动作引用排除条款，既有全局规则覆盖的验证引用该规则，未确定内容保持open。动作依据说明在该初态下为何执行此操作，以及操作如何改变验收事实。界面呈现动作明确实际入口和选择方式，目标documentId作为输入使用。完整字段及匹配规则见[动作覆盖](references/contract.md#动作覆盖)。

### 3.2 已知前提与动作输入

| 信息 | 所属位置 |
| --- | --- |
| 动作前已经成立、影响执行的事实 | 初态 |
| 本次选择的对象、填写值、目标尺寸等参数 | operation.input |
| 动作执行后才观察到、会决定不同结果的信息 | condition |
| 全图统一遵守的规则 | constraints或其直接引用的规则文档 |

当前动作只记录必需输入。此前有效的前提、全局规则和由终态表达的结果持续按其所属位置生效。


### 3.3 条件

按同一初态、同一动作名称与执行者、同一输入分组：

- 结果确定时，只登记一条迁移，省略condition。
- 动作执行后有多个可能结果时，各分支分别登记迁移及condition。
- 每个condition都应有条件不成立的其他结果分支。分支之间互斥，且终态或可观察效果存在差异。
- 动作前已知事实由初态表达；已选输入由operation.input表达。

condition记录事后结果、可匹配取值、结果样例及观察位置。响应Mock仅在结果分支需要时提供。字段省略规则与确定性计算见契约。

对照需求检查分支完整性，每个条件有不满足它的其他实际分支。相同初态、动作、输入和结果条件确定唯一终态或可观察效果；重复语义边合并。未要求的结果分支不自动增加，影响完整性的歧义按第1节澄清。

### 3.4 结果与自环

终态事实表达动作结果。只有终态未能表达的前后数据关系或额外可观察效果，才记录effects。自环须有实际可观察变化；仅重复检查同一全局规则的测试场景不另建自环。

自环的动作结果应仍满足该状态的事实；若改变了该状态用于识别或验收的事实，建立对应终态。需要表达前后数据相等、取自输入或禁止副作用等关系时，使用明确的断言。

## 4. 全局约束

constraints只记录全图统一适用的规则，每项包含id、规则陈述和直接source。已有规则文件保存的布局、外观、尺寸和适配要求通过文件及位置引用；具体值继续维护在其原文件中。

同一规则只登记一次。状态事实、动作输入、已知前提和终态结果分别保留在所属位置。下游状态和迁移沿用有效规则，不重复附加相同约束。

## 5. 建立原子需求图

完成状态、迁移和全局约束建模后，按[原子需求图规范](references/atomic-requirements.md)生成原子需求JSON及HTML。每条迁移恰对应一个“初态—迁移—终态”的原子需求。普通进入要求前项终态和后项初态引用同一状态ID；初态为正式起点的需求可随时重新进入。

使用最小费用流精确求解覆盖全部需求且访问节点总次数最少的序列，首个和重复进入均计数。原子图只保存所选序列实际使用的普通衔接和重入边；访问序列保留完整顺序及重复次数。算法、最优性依据、字段和确定性规则统一见该规范。

原子需求通过transitionId读取正式迁移，事实、内嵌operation、实际分支、直接来源及全局约束仍维护在状态图。重入是需求遍历的进入方式，不在状态图中增加业务动作。点击需求时显示从本段起点到当前到达位置的路径，侧栏省略迁移直接来源；其他HTML交互复用共用规范。

## 6. 常见问题与修复示例

审查前阅读[常见问题与修复示例](references/state-transition-examples.md)，对照修复前后的Mermaid图核对当前模型。

## 7. 审查与校验

### 7.1 语义审查

先完成第6节的示例核对，再逐项对照实际来源完成下列审查，在独立工作记录reviews中对应填写scope、facts、operations、inheritance、branches、coverage。每项status为pending、passed或failed；通过时evidence写明实际审查依据和结论。

| 审查项 | 通过标准 |
| --- | --- |
| 范围 | 图内事实、动作和规则均属于本轮要求；排除与上下文的处理符合正式来源 |
| 事实 | 主体和取值明确，可观察、可验收；视觉与功能事实完整，互斥事实分别表达 |
| 动作及结果 | 逐项核对actionAnalysis中的动作及处理结论；每条迁移有明示或必要依据，初态、操作及结果之间的关系明确，前提、输入和事后条件归属正确 |
| 前提与规则 | 已成立事实的延续有效，汇入路径前提一致，重复或已被涵盖的规则不再登记 |
| 分支与确定性 | 条件有实际其他结果，分支互斥，语义相同的初态/动作/条件只得到唯一结果 |
| 覆盖与可达 | 对照PRD全文及授权资料核对事实与动作覆盖；逐个检查entries及无边状态的独立依据；每个非起点状态有合理的到达路径 |

reviews记录六项审查结论，entries和actionAnalysis提供其中的逐项依据。来源的内容须实际支持入口、动作及结果；文件有效或引用存在不代替这一判断。逐项依据缺失、动作尚未处理或结论不成立时，相应审查保持pending或failed。

完成审查后，将实际图文件的SHA-256写入工作记录graphSha256，绑定被审查的这一版图。文件变化后核对影响，重新审查相关部分并更新哈希。未解决的歧义、缺失证据和失败检查保持未完成，处理后再定稿。

### 7.2 可执行校验

先运行独立工作校验，检查资料登记、范围映射、实际回答、审查完成度及本版图：

~~~text
python <skill-dir>/scripts/work.py check <output-dir>/state-transitions.json --workspace <project-root>
~~~

存在open问题、pending或failed审查、缺少实际回答、映射遗漏、来源失效或图哈希变化时，处理相应工作项后继续。通过结构校验不自动完成这些工作项。

| 检查项 | 校验范围 |
| --- | --- |
| Schema与身份 | 字段、版本、ID唯一性及迁移端点 |
| 直接来源 | 路径、位置、哈希、原文及UI节点引用 |
| 状态事实 | 非空事实、断言类型、视觉来源及matches-ui一致性 |
| 动作 | 内嵌字段与输入、自环的可观察效果 |
| 分支 | 同组结果互斥、条件存在其他分支、样例匹配和结果差异 |
| 起点依据 | entries与起点逐一对应，原文位置及摘录有效，依据保留在状态source中；无边状态有独立验收说明 |
| 动作覆盖 | 纳入项的动作分析已完成；每个候选动作有处理结论；已建动作与迁移的初态、operation、输入、来源及预期终态一致；每条迁移有动作依据 |
| 可达性 | 按起点标记计算图路径，各非起点状态可达；入口合理性由起点依据及语义审查核对 |
| 重复约束 | 完全重复的全局规则或状态事实 |
| 原子需求映射 | 每条迁移恰对应一个原子需求，无遗漏、重复或失效引用 |
| 合法覆盖 | 首次进入起始需求；后续普通衔接或重新进入起点均合法，全部需求覆盖，重复访问计数完整 |
| 最少访问 | 精确最小费用求解得到全局最少访问次数，序列、下界和固定选择规则一致 |
| 路线边 | 仅保留所选序列实际相邻访问对，普通衔接和重入类型及共享状态正确 |
| 双图版本 | 原子图的来源摘要、修订及引用对应当前状态图 |
| HTML同步 | 两张图的内嵌模型、哈希及共用模板内容与当前JSON一致 |

~~~text
python <skill-dir>/scripts/analyze.py validate <output-dir>/state-transitions.json --workspace <project-root>
python <skill-dir>/scripts/analyze.py render <output-dir>/state-transitions.json --workspace <project-root>
python <skill-dir>/scripts/analyze.py check <output-dir>/state-transitions.json --workspace <project-root>
python <skill-dir>/scripts/atomic.py build <output-dir>/state-transitions.json --workspace <project-root>
python <skill-dir>/scripts/atomic.py check <output-dir>/atomic-requirements.json --workspace <project-root>
~~~

校验命令只读取JSON，检查结果输出到终端；render生成状态图HTML，atomic build生成同目录原子JSON及HTML。analyze检查状态图的结构与引用，atomic检查一一映射、合法覆盖、全局最少访问、路线边裁剪与版本同步，work核对独立工作记录及其与状态图的一致性，并在finalize检查双图；输出scope标明各自检查范围。脚本检查记录齐全、引用有效和实体匹配；语义审查判断原文是否支持这些结论，两者共同用于定稿。自测通过及页面交互正常均不代替语义审查。语义审查与澄清过程不写入最终图。脚本检查与应用实际验收分别报告；未执行视觉验收时说明未执行。

### 7.3 可视化审查

生成、修改或审查状态图或原子需求图HTML前，读取[HTML设计规范](references/html-design-spec.md)，使用[Canvas页面模板](assets/graph.template.html)。页面组成、最短迁移次数分列、拖拽与置顶、聚焦可见范围、侧栏切换、详情内容及可视化验收均按该文档执行。

实际浏览器检查、模拟交互测试和模型同步检查分别报告。结构校验、文件存在或模拟测试不代表应用已实现或通过视觉验收。
