## 1. 将动作前提放进事后条件

执行“打开对象”之前，权限已经可以确定，应分别写入初态。迁移由不同初态出发，不再把权限作为动作后才出现的条件。

~~~mermaid
flowchart LR
  subgraph B["修复前"]
    B0["对象已选中"] -->|"打开对象／有编辑权限"| B1["可编辑详情可见"]
    B0 -->|"打开对象／只有查看权限"| B2["只读详情可见"]
  end
  subgraph A["修复后"]
    A0["可编辑对象已选中"] -->|"打开对象"| A1["可编辑详情可见"]
    A2["只读对象已选中"] -->|"打开对象"| A3["只读详情可见"]
  end
~~~

## 2. 同一次结果在后续迁移中重复判断

示例需求区分远程核验通过与未通过。该次结果在首次分支后已经确定，后续展示摘要、展开区域时沿用即可。若后续动作发起新的核验，新的响应结果应按需求另行建模。

~~~mermaid
flowchart LR
  subgraph B["修复前"]
    B0["对象待核验"] -->|"核验／本次响应通过"| B1["本次核验已通过"]
    B0 -->|"核验／本次响应未通过"| B4["本次核验未通过"]
    B1 -->|"展示摘要／本次响应通过"| B2["摘要可见"]
    B2 -->|"展开区域／本次响应通过"| B3["区域已展开"]
  end
  subgraph A["修复后"]
    A0["对象待核验"] -->|"核验／本次响应通过"| A1["本次核验已通过"]
    A0 -->|"核验／本次响应未通过"| A4["本次核验未通过"]
    A1 -->|"展示摘要"| A2["摘要可见"]
    A2 -->|"展开区域"| A3["区域已展开"]
  end
~~~

## 3. 结果唯一，仍为动作补充条件

需求只规定“展开后区域可见”时，直接连接初态和终态。没有实际其他结果分支，不登记“操作成功”等占位condition。

~~~mermaid
flowchart LR
  subgraph B["修复前"]
    B0["区域收起"] -->|"展开区域／操作成功"| B1["区域展开"]
  end
  subgraph A["修复后"]
    A0["区域收起"] -->|"展开区域"| A1["区域展开"]
  end
~~~

## 4. 相同初态、动作和条件得到不同终态

假设需求已明确成功与失败两种结果，按来源校正分支条件，使两者互斥。若来源本身冲突，应先澄清，再修复图；重叠条件也按同一原则处理。

~~~mermaid
flowchart LR
  subgraph B["修复前"]
    B0["数据待提交"] -->|"提交／响应成功"| B1["数据已提交"]
    B0 -->|"提交／响应成功"| B2["提交失败且输入保留"]
  end
  subgraph A["修复后"]
    A0["数据待提交"] -->|"提交／响应成功"| A1["数据已提交"]
    A0 -->|"提交／响应失败"| A2["提交失败且输入保留"]
  end
~~~

## 5. 外观相同，合并了影响后续动作的前提

若编辑权限会影响后续可执行动作，可编辑与只读场景应保持不同状态。图中的只读状态作为终点，不额外补出需求未定义的失败操作。

~~~mermaid
flowchart LR
  subgraph B["修复前"]
    B0["可编辑对象已选中"] -->|"打开"| B2["详情可见"]
    B1["只读对象已选中"] -->|"打开"| B2
    B2 -->|"修改"| B3["内容已修改"]
  end
  subgraph A["修复后"]
    A0["可编辑对象已选中"] -->|"打开"| A2["可编辑详情可见"]
    A1["只读对象已选中"] -->|"打开"| A3["只读详情可见"]
    A2 -->|"修改"| A4["内容已修改"]
  end
~~~

## 6. 将无独立验收事实的内部阶段建为状态

假设需求只验收提交结果，函数执行和请求处理中没有需验收的独立表现，可合并为一次提交迁移。若需求另有可见加载表现及验收要求，则保留相应视觉状态。

~~~mermaid
flowchart LR
  subgraph B["修复前"]
    B0["数据待提交"] -->|"提交"| B1["函数执行中"] -->|"发出请求"| B2["请求处理中"]
    B2 -->|"响应成功"| B3["数据已提交"]
    B2 -->|"响应失败"| B4["提交失败且输入保留"]
  end
  subgraph A["修复后"]
    A0["数据待提交"] -->|"提交／响应成功"| A1["数据已提交"]
    A0 -->|"提交／响应失败"| A2["提交失败且输入保留"]
  end
~~~

## 7. 仅用页面名表示状态，无法识别事实差异

将页面名补充为可观察事实，明确动作前后的区别。例中页面始终可见，变化的是详情区域的展开表现。

~~~mermaid
flowchart LR
  subgraph B["修复前"]
    B0["详情页"] -->|"展开区域"| B1["详情页"]
  end
  subgraph A["修复后"]
    A0["主体可见，详情区域收起"] -->|"展开区域"| A1["主体可见，详情区域展开"]
  end
~~~

## 8. 将全局规则的测试参数扩展为重复状态

假设规则R已完整定义适配要求，W1和W2只是验收输入，且没有其他需区分的结果：复用状态，参数检查放在规则的引用矩阵中。修复后虚线表示规则适用关系，不是状态迁移。

~~~mermaid
flowchart LR
  subgraph B["修复前"]
    B0["界面符合规则R"] -->|"设置宽度W1"| B1["界面仍符合规则R"]
    B1 -->|"设置宽度W2"| B2["界面仍符合规则R"]
  end
  subgraph A["修复后"]
    G(["全局约束：引用适配规则R"]) -.-> A0["界面符合规则R"]
  end
~~~

## 9. 用起点标记代替到达路径分析

假设需求明确：进入面板时详情收起，执行展开后详情可见；徽标组件只需独立静态展示。面板的已知入口与展开动作分别落实，徽标按独立验收来源保留为无边起点。工作记录逐项说明入口方法、动作及徽标的独立依据，不能只用起点数量或整体审查结论证明可达。

~~~mermaid
flowchart LR
  subgraph B["修复前"]
    B0["面板详情收起 · 起点"]
    B1["面板详情展开 · 起点"]
    B2["徽标静态样例 · 起点"]
  end
  subgraph A["修复后"]
    A0["面板详情收起 · 起点"] -->|"展开详情"| A1["面板详情展开"]
    A2["徽标静态样例 · 有独立依据的起点"]
  end
~~~
