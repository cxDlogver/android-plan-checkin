# 执行与依赖

## 1. 任务就绪与并发

任务计划是实现范围与依赖的依据，不能仅按编号猜测顺序。采用拓扑就绪集：前置任务局部脚本验收均通过后，当前任务才能开始。对就绪任务按计划顺序选择不冲突的批次。

任务 A 与 B 同批需满足：二者无依赖路径；写入集合不与对方读写集合相交；独占资源不相交。文件集合取 task-plan.files，资源补充设备、进程、端口、数据库、测试账号及共享会话。资源未声明清楚时先串行。目录范围需展开到实际文件并核对新增文件。独立任务合并后仍要核对共享接口与各任务验收，不能只验收最后一个任务。

示例：A 创建纯计算函数，B 创建独立展示组件且无共享写入，可并发；C 使用 A 的结果则等 A；A、B 同改配置或共用一台设备则串行。不要为了并发重排同一路线的动作。

## 2. 局部任务和完整用例

任务的 checks 验收本任务的 done，报告中用 doneIndices 标明覆盖的完成标准。用例的 acceptance.checks 验收端到端事实，报告中用 caseId、aspect、checkIndex 定位；不新建另一套需求或 operationID。

同一实现可能服务多个用例，同一用例也可能依赖多个实现任务。基础组件任务可以在其真实组件边界按对应用例标准验证该任务的责任；页面集成后再执行完整用例。局部结果登记 taskResults，不登记为用例全部通过。不得为避免依赖环降低完整用例预期。

实施完成与验收完成是两个时点。任务实现后才能编写或补齐本任务专属断言，再执行并记录；预先存在的共享驱动可继续使用。implementation.startedAt / completedAt、run.authoredAt、startedAt 与 finishedAt 表明本次顺序。时间声明需与实际操作一致，不靠修改文件时间补造过程。

若检查需要后续任务才能成立，先调整任务检查粒度，保留后续完整用例责任。无法明确本任务如何独立验收时，当前任务未具备可执行条件；不把它无依据地标为完成。

## 3. 路线与脚本边界

脚本与用例是多对多关系。优先按相同宿主、入口、数据生命周期及连续路径分组，避免每例启动应用和等待。独立 fixture 可以与其他段在同一进程顺序执行，但不能继承未经验证的业务事实。

coverage.sequence 的下标作为 visitIndex，从 0 开始。一个用例多次访问时分别记录；只看 caseId 会丢失路径上下文。一次 run 保存连续的 visits；需要重开允许入口时写明 entry，保留重放前缀的实际访问。重跑可以增加实际次数，不改变规划中的最少访问数。

每次访问先核对 given，再执行 operation，最后逐项比较 expected。given 不成立时记录失败并停止；预期不成立时保留 actual 与失败证据并停止；未到达的后项不得预填 passed。脚本运行过程中发生外部变化而破坏上下文，也应停止当前段。

本阶段可以只执行脚本检查，但不能绕过浏览器检查承担的前提证明。浏览器是唯一路径前提证明方式时，该段 blocked；不把它改成运行器伪验收。只含浏览器检查的用例仍可作为已实际执行的进入步骤，但记录为 deferred，不能作为已通过用例。

## 4. 数据、Mock 与重跑

按 dataProfiles 解析固定输入与上下文输入，保存真实对象、选择规则、环境和沿用映射。动态名称、日期、数量和版本不照抄设计图，不重新随机生成已确立对象。预期由规范与输入独立计算。

只 Mock 文档声明的外部边界，核对命中、参数、次数和恢复；不得 Mock 被测动作、目标状态或断言。计划缺少必要 Mock 定义时，补齐原用例的数据契约再执行；结论有歧义才澄清。Mock 的 UI 响应通过不证明真实存储或服务已实现。

更改实现、断言、输入资料或依赖后，核对受影响运行的快照；失效结果不能继续用于完成判断。按影响范围重跑必要任务检查和路线段，不为无关改动重复执行全图。旧失败证据保留，不用新结果覆盖原文件。
