# 代码执行规范

## 1. 输入与完成标准

读取 task-plan.json、test-cases.json、原子需求、状态图及其引用的原始资料；读取仓库指令和实际代码。使用任务规划 Skill 检查规划产物后，再初始化执行记录。已有执行记录时先校验并恢复，不重新初始化覆盖结果。

一个任务完成必须同时满足：计划范围内的代码已实现；完成标准有逐项观察结果；对应脚本已实际执行且通过；所需证据在工作区可访问。编译成功、脚本退出零、文件存在或人工修改状态均不能单独替代验收。

一个 Test Case 通过必须覆盖它全部适用检查及必要路线访问。任务的局部责任验收与完整用例验收分别记录；共享用例未完成不抹去已完成的局部任务，也不能据此提前通过完整用例。详见[执行与依赖](references/execution.md)。

本流程只执行 testType=script 的检查；browser 检查保留待验收。脚本自动控制真实浏览器仍属于浏览器验收，不在本流程执行。混合用例只完成脚本部分时记为 partial，不标为 passed；不删除或改写浏览器标准。存在未验收项时如实交付范围和原因。

## 2. 按任务实施

1. 核对任务依赖、文件范围、完成标准、检查命令及其前置任务。任务检查应能验收本任务的实现责任；若它必须等待依赖自己的后续任务才能完成，先在任务规划中拆分局部检查与后续整体验收，不制造依赖环。
2. 选择前置任务已通过局部脚本验收的就绪任务；按稳定任务顺序推进。没有前后依赖且写入文件、共享资源和运行上下文均隔离的任务可以并发。共用文件、设备、端口、数据库或路线会话时串行使用对应资源。
3. 实现当前任务，核对完成标准并记录实现完成时点。其后编写或补齐该任务的验收脚本和断言。已有测试工具、驱动和启动器可以复用，不要求重写工具；不提前以空脚本或假通过结果登记完成。
4. 按既有 Test Case 编写脚本，使用其前提、动作、预期、数据、Mock、验收类型和证据。一个脚本可以覆盖多个用例、多个任务或一段路线；不要求用例与脚本一一对应。
5. 实际运行脚本，逐检查、逐路线访问落证据，结束后立即同步结果。失败先保存失败证据，再修复受影响实现并重跑相关段；不以重复运行全部用例代替定位问题。

并发仅用于安全独立的任务或独立路线段。共用一条路径的前提不能通过并发任务各自重置来伪造。并发执行者分别写自己的脚本和运行目录，由一个汇总者串行写执行记录、用例 JSON、计划 JSON 与视图。

## 3. 合并脚本与沿路径验收

沿用 coverage.sequence 的最少访问路线及访问顺序，保留重复节点。相同环境、数据生命周期与合法连续路径优先合并进一个脚本，复用一次启动、一次就绪等待及同一上下文；断言、取证仍对应各用例和各次访问。

普通衔接核对上一用例已观察到的终态等于当前初态；只有合法起点可重新准备。脚本从非起点开始时必须先执行并记录进入该处的路径，不能直接设置目标界面。失败或中断后停止该段，后续访问保持未执行；恢复时从允许入口重放最短必要前缀，不重写原最优路线来掩盖重放。

脚本运行时持续保存已完成步骤的证据；每个验收批次结束后立即同步其覆盖用例和任务的结果，不等全部任务结束。具体分段、失败与数据沿用规则见[执行与依赖](references/execution.md)。

## 4. 证据与状态

按照[证据与状态契约](references/evidence-and-status.md)保存脚本、真实执行命令、代码与脚本摘要、解析后的测试数据、必要 Mock 记录、预期与实际对照，以及用例要求的证据。原生宿主可以采集真实截图和原生节点树；纯运行器不能冒充真实界面。原设计图仍作为预期参考图展示，不能登记为实际截图。

使用 [execution.schema.json](assets/execution.schema.json)约束执行记录；使用 [execution.py](scripts/execution.py)检查、安排就绪批次及同步视图。该工具校验引用、摘要、路线、结果覆盖和状态一致性，不运行应用、不自动判定业务语义，也不把声明的证据当作真实通过结论。

工作区最终保留：实现代码、可重跑的验收脚本、execution.json、必要的实际验收证据，以及已同步的既有 test-cases.json/html、task-plan.json/md。默认执行记录和证据位于 plan/code-execution；项目已有统一位置时沿用该位置。证据与脚本路径均相对工作区，不能只保存在系统临时目录、控制台或外部链接。

## 5. 审查与结束

核对任务范围和依赖、全部计划脚本检查的覆盖、用例所需证据、动态数据与 Mock 边界、路线连续性、结果与当前代码的一致性。只执行计划中的主用例、全局约束及有直接影响依据的回归；实际发现新的明确影响时，先补充任务规划中的依据和用例，再执行，避免额外测试扩张。

执行 check 核对 JSON、HTML 和 Markdown 同步；执行 finish 检查全部任务的脚本验收责任及脚本用例访问。未通过、缺证据、浏览器待验收和已失效结果分别陈述，不报告为全部验收完成。结构门禁通过后仍需依据原文和实际证据审查通过结论。

任务结束删除自己创建的草稿、探索脚本、临时截图及中间报告；保留能复现结论的正式脚本、失败或最终证据与执行记录。不要清理其他任务文件，不创建重复的最终报告或版本迭代说明。
