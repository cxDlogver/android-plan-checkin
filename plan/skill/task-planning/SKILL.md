# 任务规划

将确定的需求转为可以实施和验收的计划。先读[用例与数据契约](references/test-cases.md)、[代码分析与任务契约](references/task-plan.md)，生成页面时读[HTML规范](references/html-design-spec.md)。本Skill与同级requirement-analysis共同使用，复用其正式图契约、来源校验和精确路线算法。

## 完成条件

- 每个原子需求恰有一个主用例，初态、动作、实际分支和终态与正式迁移一致。
- 每个用例分别声明视觉验收和功能验收是否适用；适用时逐项确定测试类型、运行环境和结构化证据形式。脚本能够充分验收的结论采用脚本验收；需要真实浏览器的结论采用浏览器验收。
- 数据分为固定输入和上下文派生输入；Mock仅替换被测边界之外的依赖，分支结果与需求条件一致。
- 文件级任务建立在实际读取的代码链路上，并映射用例与原子需求；回归用例有直接损害的因果依据。
- 验收图完整覆盖用例，只保留精确最少访问序列使用的边。到达路径可阅读，重入与普通衔接明确区分。
- 规划文件与生成页面同步；未执行的应用验收保持not_run，代码修改和产品验收不在本次规划内自动进行。

## 1. 核对输入与范围

读取当前PRD、授权补充资料、状态迁移JSON、原子需求JSON及被引用的UI规则。运行上游校验，核对版本、内容摘要和正式来源。实现代码用于判断实现位置和影响，不自行扩大需求。

发生会改变事实、动作、结果或通过标准的歧义时，继续分析已确定部分并向用户澄清；未回答内容不能定稿。缺少字体、宿主或测试设施时，登记具体执行前置项、影响用例和完成标准，可以完成其余规划，不能将缺失当成已验收。

只使用本轮获授权的资料。每份原始资料保留直接文件位置、哈希和条款定位；状态与迁移事实通过绑定的正式图读取，不复制一份可独立漂移的需求。

## 2. 建立Test Case

按原子需求顺序建立主用例。given引用迁移初态，operation保留迁移内嵌动作，expected引用终态并覆盖迁移effects。原子需求里的实际condition决定Mock或真实结果准备；单一确定结果不添加占位条件。

给出初态的观察和准备方法、动作入口、可判定的预期和取证位置。普通路线继承已验收终态及同对象数据；只有起始用例可以重新准备入口。测试框架的beforeEach不能把任意非起点伪造成路线入口。

全局约束保持单一来源，以专门用例覆盖规则矩阵，不在每个主用例中重复相同条款。回归用例按第5节判定，不与主需求重复计数。字段见[test-cases.schema.json](assets/test-cases.schema.json)。

## 3. 选择验收方式与数据

逐项结论选择脚本验收或浏览器验收。脚本验收运行明确的命令、测试或设备驱动，覆盖规则、组件协作及原生应用检查；浏览器验收在真实浏览器页面中完成交互与观察，也可以由自动化脚本驱动。真实浏览器中的验收统一归为浏览器验收，不因采用自动化工具而改称脚本验收。

同一个主用例分别登记acceptance.visual和acceptance.functional，各自记录适用性、理由及检查。每项检查明确脚本验收或浏览器验收，以及执行环境和截图、DOM、原生节点树、断言报告等证据形式。不适用的一类写明理由并保留空检查，不为凑齐两类而增加业务效果。视觉呈现和呈现切换仍属于视觉验收。

同一用例可以有多项检查，不因验收方式拆出多个原子需求。记录充分性理由、步骤及独立预期计算方式；验收结果与证据相互对应。具体选择规则见[验收分类、类型与证据](references/test-cases.md#21-视觉与功能验收)。快照存在、代码返回成功或Mock直接返回目标界面均不能证明需求已实现。

数据和Mock按[数据与Mock规范](references/test-cases.md#3-测试数据与mock)填写。固定枚举可固定；与对象、时钟、前序事实或实时页面有关的值从明确上下文解析。不得从被测输出反推预期再与其自身比较。

## 4. 分析代码与拆分任务

从实际入口追踪到呈现、事件、状态、服务及外部边界，记录文件哈希、行号、读取到的符号或片段及其作用。明确哪些环节需要改变，哪些只作为依赖保留；导入关系不等于修改责任。

任务按可验证的结果拆分，写明文件范围、具体改动、依赖、主需求与用例、完成标准和将来执行的命令。新增文件注明新建并说明挂载位置；不能把计划中的文件伪装成已读取代码。实现步骤不能替代验收步骤。

## 5. 判定直接影响与回归

对每个拟修改边界判断：原有哪个行为依赖它；本次具体修改怎样可能破坏这个行为；哪个输入能暴露损害。三者明确且不已被主用例覆盖时，建立定向回归用例并关联impact及相关任务。

仅因同处调用链、同一模块或共享数据类型，不增加回归。保持不变的模块说明不变依据；若实施时扩大文件或行为范围，重新审查影响并更新计划。存量功能的保留由参考代码确定，不把它转换为本轮新增业务需求。

## 6. 生成最少访问验收路线

主用例普通衔接仅允许前项终态等于后项初态；起始用例可随时重新进入。主路线映射已验证的原子需求最优序列，保留重复访问和顺序。

独立全局检查及回归用例必须有完整隔离准备方法，在主路线之后各访问一次；它们不能向非起始主用例提供捷径。此时下界为主路线最少访问数加独立用例数，所选序列达到该下界。脚本同时复用精确最小费用算法校验总下界。

需要继承前序事实的补充检查应并入对应主用例的验收检查；确实代表新需求迁移时先完善上游需求模型。不能把有业务前置路径的测试标成独立入口来降低次数。

最少次数统计逻辑用例访问，包含重复访问；不表示环境矩阵行数、测试断言数、截图数或执行时间最少。只保存选定序列相邻出现的唯一边，重复次数保留在sequence。详见[路线契约](references/test-cases.md#4-验收路线)。

## 7. 审查与门禁

先做语义审查，再运行确定性校验。脚本检查结构和引用，不能代替判断验收方法是否充分、Mock是否越界、回归因果是否成立、任务是否可实施。

| 门禁 | 通过标准 |
| --- | --- |
| 输入 | 上游校验通过，引用哈希与定位有效，范围没有被代码现状扩大 |
| 主用例 | 一需求一用例，初态/动作/终态一致，分支仅在实际条件存在时出现 |
| 验收 | 每例视觉/功能适用性明确；适用检查具有测试类型、环境、独立判定和证据形式；方法足够证明所述结论 |
| 数据/Mock | 类型与来源明确，动态值无固定替代，Mock值命中对应分支且不替代被测行为 |
| 代码/任务 | 读取证据有效，修改路径明确，任务依赖无环，用例及需求映射完整 |
| 回归 | 直接受损机制及暴露输入明确，无仅因链路涉及而泛化的测试 |
| 路线 | 全覆盖、合法进入、精确最少、仅保留所选边 |
| 交付 | JSON/HTML/Markdown同步；侧栏以可读文字呈现到达路径、前置位置、动作、结果、测试与证据、状态；终态存在UI图时展示预期参考图，不展示来源和技术映射；无伪结论或临时产物 |

~~~text
python -B <skill-dir>/scripts/plan.py build <output-dir>/test-cases.json --workspace <project-root>
python -B <skill-dir>/scripts/plan.py check <output-dir>/test-cases.json --workspace <project-root>
python -B <skill-dir>/scripts/test_plan.py --temp-root <workspace-temp-dir>
node <skill-dir>/scripts/test_canvas.js <output-dir>/test-cases.html
~~~

build只派生路线、HTML与Markdown，不自动生成需求判断或代码任务。check不修改文件。校验结果打印到调用输出，不额外沉淀报告。任务规划完成不表示产品通过验收，所有用例execution.status保持not_run。

## 8. 最终产物与清理

项目目录仅保留test-cases.json、test-cases.html、task-plan.json、task-plan.md。前两者用于验收图，后两者用于文件级实施计划，字段见[task-plan.schema.json](assets/task-plan.schema.json)。

Skill本身保留规范、Schema、渲染模板和校验自测脚本。完成后删除本任务创建的澄清工作副本、一次性生成脚本、临时测试目录及调试截图；已有原始资料和其他任务产物不属于清理对象。仍有影响定稿的未决问题时，保留工作记录供继续处理，不宣称任务已完成。
