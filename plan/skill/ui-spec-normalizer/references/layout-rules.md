# 确定性的双端分类与布局规则

## 1. 唯一分类断点

本Skill固定使用768逻辑像素作为唯一宽度分类断点，这是规范约定，不是设备型号或行业标准推断。

| 完整页面可用逻辑宽度W | 唯一类别 |
| --- | --- |
| 0 < W < 768 | mobile／手机端 |
| W >= 768 | desktop／桌面端 |

W必须为正的有限数。不将W取整或四舍五入后再分类；767.999属于手机端，768属于桌面端。高度、长宽比、画板标题、导航形态及运行平台不参与分类。

执行顺序：

1. 识别完整screen，排除组件、说明板与多个页面组成的拼版。
2. 读取画板逻辑尺寸；只有明确导出倍率时，才用图片像素除以倍率。
3. 用W与768直接比较，写入mobile或desktop profile。
4. 组件继承所属页面类别，不能根据一个按钮的宽度判端。被两类使用的组件分别建立所属类的记录。
5. reference说明资源沿用关联上下文，不作为页面分类输入。其自身宽度不能改变页面类别。
6. 尺寸或倍率缺失时记录关键issue，等待取得尺寸；保留draft与来源清单，不创建第三种类别或猜测倍率。

示例：

- 375×812页面：mobile。
- 767×1200长页面：mobile。
- 768×600页面：desktop。
- 1440×3200长页面：desktop。
- 图片宽750、明确2倍导出：逻辑宽375，mobile。
- 某设备的实际可用宽度800：desktop，不另设平板类。
- 200宽的独立按钮：继承所属页面，不自行判为手机页面。

## 2. 分类数据与单位

rules.classification固定为：

```json
{
  "breakpoint": 768,
  "unit": "logical-px",
  "mobile": "0 < width < 768",
  "desktop": "width >= 768"
}
```

rules.profiles只允许mobile与desktop两个键；每个profile.formFactor与键相同。没有另一类来源时不生成虚构UI。运行／参考环境同样按可用逻辑宽度匹配类别，缺少对应类的UI时报告未提供，不退回另一类缩放。

document.referenceSize是完整页面的逻辑宽高。screen.profileId必须等于根据referenceSize.width计算出的类别。profile基准宽度和每条validationCase.width也必须落在该类区间。

几何和字号统一为logical-px；1个logical-px表示规范中的1个逻辑像素。导出倍率不改变这个单位。源资料使用其他相对单位时，按明确上下文换算并保留换算依据；上下文缺失则记录issue。

## 3. 唯一布局的选择顺序

每个document只有一棵规范树。按照以下顺序选择，每个容器只记录一种结果：

1. 存在明确覆盖关系：该覆盖容器使用Overlay，子项记录锚点。
2. 需要二维轨道、跨行或跨列：使用Grid。
3. 单行、单列、等权分配或自然换行：使用Flex。
4. 无法区分但可按一维关系表达：使用Flex，并将该选择记录为normalized决策。

来源已有明确结构时据其意图归一；不能以目标运行平台为由保留两套布局。不同容器可以使用不同布局，禁止在同一容器内保存候选实现或layoutOptions。

页面、卡片、字段、按钮等默认使用flow。anchored仅用于明确覆盖并记录anchorId、边、偏移和层次；fixed必须明确相对viewport固定；sticky必须明确所属滚动容器与阈值。锚点不能缺失、跨document或形成循环。

图形内部的SVG／画布坐标属于资源几何，不属于页面绝对定位。不得用来源观测坐标拼装整个页面。

## 4. 尺寸、样式与响应式对齐规范

每个节点必须写清楚三件事：哪些值固定、哪些尺寸按公式计算、哪些属性在指定条件下切换。后续实现按这些规则计算和对齐；规则不足时补充决策或issue，不由实现者临时选择。

**（1）先选择端型，再计算页面布局**

完整页面可用逻辑宽度W < 768时使用mobile；W >= 768时使用desktop。两类分别维护自己的节点树。

同一端型内部允许布局断点。例如桌面端在1024以下显示两列、1024及以上显示三列，两者的profileId仍然都是desktop。1024只影响列数，不增加端型。所有条件中的width均指完整页面可用逻辑宽度；组件自身宽度由父容器分配，本版不使用组件宽度作为mode条件。

**（2）按下面的规则保存每个节点**

| 对象 | 必须保存的规则 | 空间变化时的处理 |
| --- | --- | --- |
| 颜色、圆角、描边、阴影 | 用styleRef引用确定的视觉值 | 宽度变化时保持原值；主题或状态需要另一套值时，明确条件并切换到指定styleRef |
| 文字 | 字体、基准字号、字重、行高；换行方式、最大行数、溢出处理 | 宽度变化时基准字号保持不变；允许换行的文字增加行数，由content高度撑开。单行省略必须明确maxLines=1、overflow=truncate |
| 图标 | 资源、固定逻辑宽高，例如24×24 | 保持尺寸与比例；需要另一尺寸时必须记录切换条件及目标值 |
| 容器 | 唯一Flex/Grid/Overlay布局；对齐、padding、gap；宽高计算方式 | 按已写明的宽高规则计算。列数、方向、间距确需改变时，记录条件和覆盖值 |
| 图片 | 资源、容器宽高、fit和focus | contain完整显示且允许留白；cover填满并按focus裁剪；stretch允许变形，仅在明确要求时选用。需要固定比例时，将比例及计算方式记入有文档语义的extension，不能只写“自适应” |
| 滚动与环境遮挡 | 哪个节点负责滚动、滚动方向；安全区域和键盘避让规则 | 内容超过可用高度时按指定容器滚动；环境提供实际遮挡尺寸。同一遮挡只预留一次 |

scaleWithSystem=true的文字按环境fontScale放大：字号和长度型行高乘以fontScale，倍数型行高保持倍数。文字放大后按原换行、撑高和滚动规则重新排版；宽度变化本身不触发字号缩放。

**（3）宽高必须落成一种可计算方式**

所有长度均使用logical-px。min/max作用于当前选定的尺寸，不是第二套候选布局。

| JSON尺寸方式 | 具体含义 | 示例 |
| --- | --- | --- |
| fixed | 使用value指定的固定长度 | 图标宽24：mode=fixed、value=24 |
| fill | 填满父级分配区域，再受min/max限制 | 正文区宽度填满，最大1200；父级明确居中 |
| content | 内容和内边距决定尺寸，再受min/max限制 | 多行文字或卡片高度随内容增加 |
| fraction | 在当前布局分配的剩余空间中按权重计算 | 两列权重1、2，去掉padding、gap和固定轨道后按1:2分配 |
| percent | 父级内容区域的相应尺寸乘以value | 宽度value=0.5表示父内容宽度的50% |
| viewport | 使用当前可用窗口的相应尺寸，再受min/max限制 | 页面根节点使用可用窗口高度 |

fixed/fraction/percent必须填写value；其他方式value=null。min/max没有约束时为null。父尺寸、固定项、间距扣除顺序必须明确，不能用一张截图中的子节点坐标代替计算关系。

空间不足时，严格执行节点声明的换行、条件切换或滚动策略。缺少处理规则就记录issue，不能临时缩小字号、压扁图标、截掉正文或修改间距。

**（4）条件变化必须写明“何时切换、改什么、改成多少”**

将条件写入profile.modes，将该节点的目标值写入responsive.overrides。mode就是一条有名称的条件规则。

- 优先使用填充、限宽和自然换行；明确需要改变列数、方向或其他属性时才增加布局断点。
- 每条断点决策在rules.decisions中说明依据，节点用decisionRefs引用。单张截图推导出的规则标为normalized。
- 宽度区间采用左闭右开[min,max)，例如[768,1024]表示768 <= W < 1024；null端点表示在当前profile内不设该侧边界。
- 同一profile的全部mode条件必须互斥。宽度与主题需要组合变化时，写出互斥的组合条件，不能依赖未定义的覆盖优先级。
- 没有mode命中时使用节点本体base；命中一条时，仅覆盖明确列出的字段，其余规则保持base。
- policy.locked锁定JSON中的值或计算规则；policy.adaptive列出允许被条件覆盖的字段路径。没有列入adaptive的字段不得被mode覆盖。锁定fill计算规则时，其渲染宽度仍会随父区域按该规则计算。
- responsive不改变id、parentId、children或profileId。节点增删或父子关系不同的页面另建身份明确的document，并写清选择条件；不能留下多个待选结构。

**（5）一个具体例子**

假设已确定一份桌面页面规则：卡片区域最大宽1200、父级居中、四边padding=24、行列间距=16；768 <= W < 1024显示两列，W >= 1024显示三列。字号和图标尺寸均保持其基准值。

下面是JSON片段：modes写入rules.profiles.desktop.modes；node内字段写入实际卡片容器，其余必填节点字段按节点契约补齐。1024为本例已确定的布局断点，不是所有页面的默认值。

```json
{
  "modes": [
    {"id": "compact", "when": {"width": [768, 1024]}}
  ],
  "node": {
    "sizing": {
      "width": {"mode": "fill", "value": null, "min": null, "max": 1200},
      "height": {"mode": "content", "value": null, "min": null, "max": null}
    },
    "layout": {
      "type": "grid",
      "columns": [
        {"mode": "fraction", "value": 1},
        {"mode": "fraction", "value": 1},
        {"mode": "fraction", "value": 1}
      ],
      "rowGap": 16,
      "columnGap": 16,
      "padding": [24, 24, 24, 24]
    },
    "policy": {
      "locked": ["styleRef", "children", "sizing", "layout.type", "layout.padding", "layout.rowGap", "layout.columnGap"],
      "adaptive": ["layout.columns"]
    },
    "responsive": [
      {
        "modeId": "compact",
        "overrides": {
          "layout": {
            "columns": [
              {"mode": "fraction", "value": 1},
              {"mode": "fraction", "value": 1}
            ]
          }
        }
      }
    ]
  }
}
```

计算结果必须唯一：卡片区域宽度B=min(父级分配宽度,1200)；每列宽度=(B-48-(列数-1)×16)/列数。W=900时两列，W=1024时三列；卡片区域宽度达到1200后保持1200，多出的空间由父级居中分配。高度按内容增加。

验收本例时检查W=768、900、1023、1024、1440，以及长文字和字体放大：列数满足条件，padding始终24、gap始终16，文字不被擅自缩小，内容按声明换行或滚动。结构校验与实际渲染检查分别记录结果。


## 5. 验收

分类必须自动检查767与768两侧，确认不存在重叠或空档；有两类profile时分别检查，只有一类时明确未提供另一类。

结构验证只证明JSON内部一致。基准视觉固定profile、referenceSize、字体、主题、语言与样例内容；适配另检查类内连续宽度变化、文字放大、长文案和环境遮挡。

本规范不预设通用相似度百分比。没有实际执行的视觉检查保持not-tested。
