# UI Spec Normalizer

把设计资料转换为后续实现与验收可执行的JSON规范。使用确定性的双端分类，不记录运行平台，不根据设备型号、操作系统、标题或导航形态改变分类。Schema版本为2.0.0。

## 完成条件

先固定输入范围、页面清单和输出目录，再转换：

- 完整页面按逻辑宽度唯一分类：0 < width < 768为mobile，width >= 768为desktop。
- 只保留mobile与desktop两类；组件继承所属页面类别，说明板不参与分类。
- 每个节点在每个有效环境下只有一个布局和定位结果，不保留候选树。
- JSON完整表达节点层级、尺寸、样式、内容、资源和适配规则。
- 分开报告结构、发布就绪度、基准视觉、响应式视觉；未经执行不能标记通过。
- 用户要求切换JSON基准后，原始资料只作来源留档。

## 1. 确定边界和逻辑尺寸

仅扫描用户授权来源，排除历史目录；使用指定输出位置，未指定时选择工作区独立ui-spec目录。

优先通过设计连接器读取结构、变量、组件和截图。受保护的原生设计文件仅经支持工具访问。HTML是转换输入，截图只证明可见事实。

从源画板取得逻辑宽高；只有明确倍率时才将图片像素除以倍率。没有倍率或完整页面尺寸时，先查来源；仍无法取得则记录关键issue、保存draft，不猜测倍率或填写第三类端型。

页面较多时按页持久化；恢复前核对来源版本。只请求方法讨论时解释规则，不自动转换整个项目。

## 2. 执行唯一断点分类

阅读[布局决策指南](references/layout-rules.md)并严格执行：

- 使用完整页面的逻辑宽度W，不使用物理像素、局部组件宽度或拼版总宽度。
- W < 768归mobile；W >= 768归desktop；W必须是正的有限数，不先四舍五入。
- 高度只用于布局和滚动，不参与分类。运行平台字段platform及其替代字段均不进入规范。
- rules.profiles只能使用mobile、desktop两个键；只生成实际有输入的类别。
- 运行或参考环境按页面可用逻辑宽度使用同一断点；不根据浏览器、设备或操作系统改判。
- 两类UI独立。缺少另一类UI时明确未提供，不机械缩放现有稿补齐。

几何与字号统一使用logical-px；来源单位先换算再沉淀。实现侧的单位映射不属于分类字段。

## 3. 确定唯一结构

按[布局决策指南](references/layout-rules.md)的顺序选择容器结构。明确覆盖关系使用Overlay，真正二维轨道使用Grid，一维关系使用Flex；无法区分的一维结构以Flex为归一化选择。普通定位使用flow，浮层等有明确锚点时才使用其他定位。

分类不直接决定布局引擎。不得写“Flex或Grid均可”作为最终规则；每个容器只记录一个layout。

按[尺寸、样式与响应式对齐规范](references/layout-rules.md#4-尺寸样式与响应式对齐规范)逐节点确定固定值、尺寸计算方式与条件覆盖。768仅作为端型分类断点；类内优先连续适配，需要布局断点时记录互斥width条件和明确覆盖值。仅允许覆盖policy.adaptive声明的字段，base为唯一兜底。

分别记录固定视觉参数、流动尺寸、文字策略、滚动归属和环境遮挡规则。单稿未说明的规则可在用户授权范围内制定，记为normalized决策，不能伪称提取事实。改变信息结构的关键缺失保留issue，继续可独立完成的部分。

## 4. 最终产物

阅读[节点与交付契约](references/node-contract.md)，使用[通用Schema](assets/ui-spec.schema.json)生成本次范围内的最终规范包：

- manifest.json：版本、来源、document清单与哈希。
- rules.json：固定classification、两类profile、环境和已确定决策。
- library.json：视觉配方与资源。
- documents/具体标题.json：每页／每组件唯一结构及referenceSize。
- schema/ui-spec.schema.json：本Skill的Schema副本。
- UI规范.md：分析结论、当前规则、节点语义、适配与验收方法。
- validation-report.json：实际校验结果、未执行项和影响交付的缺失。
- assets/：最终JSON或报告需要随包使用的资源与证据，按需保留。

保持ID稳定、children有序、parentId正确。完整保留文字、矢量／图片、效果、布局和已捕获状态；无法表达的属性使用有明确语义的extension或issue，不静默丢弃。

JSON不依赖运行时回读原稿。需要随包使用的资源复制或内嵌，字体等依赖的可用性如实记录；缺失项按实际影响写入issues，不为补齐产物扩展任务。

分析说明合并到UI规范.md，校验结论汇总到validation-report.json。来源标识、版本和必要观测保存在sources/source字段，通常无需另交原始节点快照、转换脚本或过程报告。用户要求的附加产物按其范围保留。

## 5. 校验与规范切换

运行 `python <skill-dir>/scripts/validate_spec.py <output-dir> --report <output-dir>/validation-report.json`。脚本只读取包内JSON和资源，检查固定断点、端型一致性、字段、引用、资源、布局与适配条件。

覆盖767与768的分界；只提供一类UI时，检查该类边界并明确另一类未提供。再按实际目标检查长文案、字号、环境遮挡和连续宽度变化。未执行的视觉检查保持not-tested。

关键issue解决、依赖可用、结构完整后才能发布canonical；draft保留可用结果和阻塞项。宽度不足以分类的来源留在issues中，不创建undetermined类型的document。

用户要求只按JSON对齐时，更新实际工作入口并将旧资料标为来源留档。维护时修改当前JSON，不从旧稿覆盖人工修订；只有明确的新版本迁移才重新导入来源。

## 6. 维护与失败处理

- 本版契约为2.0.0；旧版运行平台、平板或未确定分类字段不能混入新包。
- 修改后更新哈希并重新检查；结构通过不能替代视觉通过。
- 连接器失败可使用已授权且有版本依据的本地导出；信息不足保存draft，不宣称完整转换。
- 工具策略拒绝预览时记录限制，不绕过。
- 只建立规范；未经另行要求不改应用代码、不安装全局Skill、不发布结果。
- 修改校验脚本后运行[自测](scripts/test_validate_spec.py)；受限环境可用--temp-root指定可写临时目录。
- 任务完成后删除本次生成的中间快照、抓取缓存、临时脚本、调试文件、重复截图和过程日志；保留最终交付依赖的资源、必要验收证据及用户原有资料。仍在续做的任务可暂存恢复所需信息，完成后清理。

交付说明规范入口、覆盖、固定断点和实际检查结果。
