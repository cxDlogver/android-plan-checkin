# 逐节点分支审查与收敛

## 建模次序

先从来源识别功能能力、进入状态和主流程，建立初版状态与迁移，并同步建立原子需求。随后运行多轮逐节点审查，补充有意义的边界。审查是 AI 的内部工作，只有初始澄清和最终验收需人工作出确认。

逐迁移和逐来源的合法执行与有效分支覆盖规则以 [semantic-validation.md](semantic-validation.md) 为准，不得将本文件的节点十维审查当成最终完整性证明。

每轮审查开始时冻结 nodeIds，即当前全部状态 ID。逐节点、逐维度登记结论；本轮新增节点下一轮继续审查。修改状态事实或迁移守卫后，把该节点、关联迁移两端和受影响的共享节点纳入后续检查。为便于证明覆盖，闭合轮仍须全量复核，不只检查最近修改项。

## 每个节点的检查维度

每一维度都须有记录；不适用时说明本功能中的具体原因，不能用统一空话跳过。

| dimension | 检查内容 |
| --- | --- |
| sources | 已知 PRD 条款、UI 场景和人工作答是否覆盖；是否冲突或重复 |
| events | 此状态下用户／系统能触发的事件、无效事件、事件后可观察响应 |
| guard_complement | 现有守卫的补集在合法域内是否有定义；分支是否漏、重叠或冲突 |
| boundaries | 空／非空、零／正数、阈值内外、首次／末次等是否产生不同规则 |
| failure | 拒绝、失败、超时、部分成功是否适用且有依据；哪些副作用禁止发生 |
| cancel_return | 取消、返回、撤销、恢复是否有业务意义及来源；不可逆是否需明确 |
| repeat_time | 重复触发、重试、过期、时间变化、操作顺序是否改变允许行为或结果 |
| permissions | 角色、权限、资源归属等约束是否适用；单用户功能可以有依据地不适用 |
| ui | 可观察状态是否与画板、组件或视觉状态对应；缺稿是否明确标注 |
| cross_feature | 跨功能共享状态、汇合、回环、真实入口、逐边可执行见证与结束边界是否一致 |

检查反面不等于机械翻转。例如“有问题项则拦截”需要检查“无问题项”时是否仍因其他条件拦截；不能直接宣布无问题就一定提交成功。可暂停不必然意味着可恢复，可删除不必然意味着可撤销。

## 何时增加分支

一个候选分支至少应改变以下一项：允许操作、守卫约束、业务事实、可观察 UI／结果、禁止副作用、后续可执行迁移、独立验收结论。

新增时记录 meaning，说明它覆盖了什么与已有分支不同的义务，并给出来源或待决定问题。若“1个”和“5个”在当前抽象下都满足同一守卫、行为与结果，不拆成两条需求；它们可成为同一需求的示例数据。零项与有项若导致不同允许操作，则可能需要分支。

数量本身若是必须展示的状态属性，使用参数化事实或等价类表达，只有改变可验收义务时才分裂结构，避免穷举所有数值。不得为凑边界清单制造没有依据的保存失败、并发、权限或恢复需求。

持久规则、公共视觉约束可以复用规则／UI 引用，不必复制节点或造自环。两个节点是否等价取决于已确认抽象和行为，不只是标题文字相同。

## 检查结论 disposition

- covered：已有状态／迁移／需求覆盖，relatedIds 指向对应实体。
- added：本轮新增了有意义实体；记录 differences、来源和 changes。
- pending_decision：资料不足，question 记录问题、候选及依赖；不把未知答案当事实继续推导。
- excluded_equivalent：与已有分支等价，说明为何验收义务相同并引用已有实体。
- not_applicable：说明本维度为何不适用于该节点。

reason 不得留空。evidenceIds 指向 sources；当确实只能由人决定时关联 question，并明确证据缺口。一个检查可以关联多条迁移；同一维度也可有多条检查记录。

## 逐迁移、逐来源与候选衔接审查

每条非候选迁移须有可追溯的 execution witness，包含真实入口、完整路径、业务场景数据、逐步事件／守卫／结果理由。无见证不能简单标为有效：依次排查入口、缺少前置操作、状态粒度、条件与终态事实；确证无效则删除对应迁移和原子需求并记录 remove；不确定则 question + candidate。

对 PRD/UI 及影响需求的人工作答按可定位条款维护 coverageClaims，记录已覆盖的原子需求、等价排除、明确范围外或待决；不能用无具体条款的一条汇总声明掩盖缺口。由独立评审核查条款拆分是否充分，程序仅能验证引用。

对原子需求图所有结构候选衔接维护 continuationAssessments：连续见证须确实包含相邻两条迁移；不兼容的排除须记录语义依据；未判定的保持 pending，不可发布。结构等式仅是候选关系。

任何含义变化，受影响节点、边、见证、来源覆盖及衔接结论全部标记需复审；见证、覆盖结论和衔接处置进入 semanticDigest，不能仅更新 HTML。

## 每轮记录

rounds[] 每项包含：

```text
id, revision, kind(build|audit), nodeIds[], checks[], changes[], openFrontier[]
```

build 记录初版主流程来源与结构变化。audit 为全量逐节点补漏；每个 nodeId 的十个 dimension 均有结论。changes 记录 add/update/remove 的实体、meaning 及 sourceIds。新增或修改后不得在同一轮直接宣称闭合，要在更新版本上再进行全量审查。

完成一个节点就用 workflow.py checkpoint 的 node_audit 单元保存，不等全部审完才补过程。节点审查不能同时改语义，先保存变更再以新摘要检查。闭合要求所有节点有该轮／该摘要的已保存审查。历史删除 ID 按 model-contract.md 的 retiredIds 和删除记录追溯，不忽略未知引用。

openFrontier 表示仍需继续分析的节点／实体；业务规则待决但已完成当前可分析工作的情况，可以移至 questions，不伪装成问题已解决。保持分析前沿与人工待决清单两者可区分。

## 进入最终审阅的条件

可以产出带待决项的 review_ready 草案。须说明：哪些分析已收敛，哪些分支仍因业务解释未定而是 candidate；不能将“可供人审阅”写成“需求已确认”。

review_ready 也必须有下面的闭合覆盖；pending_decision 可用于集中澄清，但 QUESTION-001 未通过不请求整体确认。空 rounds 或未完节点保留 analyzing/incomplete。

本轮无新增的闭合证据是：

1. 最后一次结构／含义变更之后，在当前 revision 上完成一个全量 audit 轮；此前至少还有一个建模／审查轮。
2. 该轮覆盖当前全部状态及全部适用维度，不存在未审的新节点。
3. 该轮 changes 和 openFrontier 均为空；guard、边界及反向检查都有处置理由。
4. 未决业务语义和设计缺口完整列在 questions，未被隐含选定；UI、功能与原子需求的对应可追溯。
5. 全部正式有效迁移有完整执行见证；全部来源行为义务有具体 coverageClaim；全部结构候选衔接已分类，不得将无见证／无依据的边当已验证有效。
6. 在完整当前范围做来源→迁移的反向检查，不能只验证图上已有的边。

在全量复核后运行以下命令，将摘要写入该轮 modelDigest；加入该字段本身不会改变摘要。含义再次变更时摘要失效，必须更新 revision、重审和导出。

```text
python <skill-dir>/scripts/model_tools.py digest <analysis-model.json>
```

最终 confirmed 版本的闭合轮不应仍有 added 或 pending_decision 结论；曾经待决的项应根据人工作答更新为对应覆盖／排除结论。

最终确认之前，用户须处理影响当前正式模型的待决项：给出答案、选定候选或明确移出范围。任何导致模型含义改变的答案都触发重审和重新导出；最终确认须覆盖重审后的版本。

预算或时间不足、资料无法访问、抽象边界不清时，可以保留 incomplete 和精确前沿。不能设置“做满三轮就完整”或“连续两轮 AI 没想到就必然无遗漏”的结论。闭合只表示在已确认范围、来源、抽象粒度下完成了可复核审查。
